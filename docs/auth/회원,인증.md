## 1. 목표

> 과제 조건: "회원가입과 로그인·로그아웃 기능을 구현하고, 인증된 사용자가 본인에게 허용된 정보와 기능을 이용할 수 있도록 한다."

- 이 파트가 책임지는 것:
  - 회원가입: 실제 은행 앱의 가입 흐름을 참고해 필요한 정보를 입력받고, 중복·형식 검증을 거쳐 사용자를 생성한다.
  - 로그인·로그아웃: 첫 로그인은 아이디·비밀번호로 인증하고, 성공하면 간편비밀번호(6자리)를 설정해 이 브라우저를 등록 기기로 저장한다. 이후에는 등록 기기에서 간편비밀번호만으로 로그인한다. 로그인 상태는 세션으로 유지하고, 로그아웃 시 세션을 종료한다.
  - 본인 정보 보호: 로그인한 사용자가 자신의 계좌·카드·거래·대화 내역만 보고 조작할 수 있게 한다. 타인의 데이터는 URL을 직접 입력해도 접근되지 않아야 한다.
  - 인증 관련 자연어 요청 처리: "로그아웃 해줘", "비밀번호 바꿔줘" 같은 요청을 직접 처리하거나 해당 화면으로 안내한다.
  - 인증 실패 상황의 동작 정의: 중복 가입, 비밀번호 오류, 세션 만료, 미인증 접근 등에서 사용자에게 무엇을 보여줄지 정한다.
- 이 파트가 다른 파트에 제공하는 것(공통 규칙):
  - users 테이블과 user_id: 계좌, 카드, 거래, 대화 기록 등 모든 테이블이 user_id로 사용자와 연결된다. (DB 담당)
  - 접근 제어 규칙(6장): 모든 조회·변경은 세션의 user_id 기준으로 필터링한다. 네 명이 각자 구현할 때 동일하게 적용한다. (전원)
  - 로그인 필요 API 보호 방식: FastAPI 의존성 `Depends(current_user)` 하나로 통일해 모든 라우터에서 같은 방식으로 쓴다. (전원)
  - 미인증 상태의 자연어 요청 처리 기준: 로그인하지 않은 사용자의 요청에 어떻게 답할지 정한다. (자연어 담당)
  - 2차 인증: 이체 등 중요 동작 직전에 간편비밀번호를 한 번 더 확인하는 화면과 함수를 제공한다. 로그인에 쓰는 6자리를 그대로 재사용한다. (계좌 담당)

- 완료 기준:
  - 가입 → 아이디·비밀번호 로그인 → 간편비밀번호 설정 → 보호된 화면 이용 → 로그아웃 흐름이 끊김 없이 동작한다.
  - 로그아웃 후 같은 브라우저에서 다시 접속하면 간편비밀번호 6자리만으로 로그인되고, 다른 브라우저에서는 아이디·비밀번호를 요구한다.
  - 로그인하지 않으면 보호된 화면과 데이터에 접근할 수 없다.
  - 로그인한 사용자가 다른 사용자의 데이터를 어떤 경로로도 볼 수 없다.
  - 10장의 실패 시나리오가 모두 기대한 대로 동작하고, 그 결과가 README에 기록된다.

### 2.1 우리 프로젝트에 반영할 것

- **로그인 구조는 전통 은행 앱 + 간편 로그인 혼합**: 첫 로그인은 아이디·비밀번호(전통 은행 방식), 그 뒤에는 토스·카카오뱅크처럼 간편비밀번호 6자리만 입력한다. 휴대폰 본인인증과 보안 칩은 없으므로 "기기 등록"은 서버가 발급한 장기 쿠키로 대신한다. 내부 방식은 **서버 검증형 간편비밀번호 + 기기 등록 쿠키**다(5.1).
- **가입 화면은 토스 방식**: 한 화면에 입력을 하나(또는 한 묶음)씩만 받는 단계형 UI로 구성해 모바일 앱 느낌을 낸다. 서버 렌더링이라면 단계별 페이지 또는 한 페이지 안의 단계 전환으로 구현한다.
- **약관 동의는 카카오뱅크 방식**: 전체 동의 체크박스와 필수·선택 항목 구분을 둔다.
- **본인인증은 흉내만 낸다**: 이름·생년월일·휴대폰 번호를 입력받되 실제 문자 인증은 하지 않는다. "인증번호 입력" 화면을 두고 고정값(000000)으로 통과시킨다.
- **2차 인증(간편비밀번호)**: 이체 등 중요 동작 전에 로그인에 쓰는 것과 같은 6자리를 다시 요구한다. 세 앱 모두 로그인 PIN과 거래 PIN이 같은 구조다.
- **가입과 계좌 개설 분리**: 카카오뱅크처럼 회원가입만으로 끝내고, 계좌 개설은 계좌 파트의 별도 흐름으로 넘긴다.

## 3. 범위

### 3.1 구현하는 기능

| ID | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| AUTH-01 | 회원가입 | 단계형 화면에서 약관 동의, 아이디, 비밀번호, 이름, 생년월일, 휴대폰 번호를 입력받아 사용자를 생성한다. 아이디 중복과 비밀번호 규칙을 검증하고, 비밀번호는 해시로 저장한다. 가입 완료 시 자동 로그인 후 홈으로 이동한다. | 필수 |
| AUTH-02 | 로그인 | 두 가지 방식을 제공한다. (a) 아이디·비밀번호 로그인: 등록되지 않은 브라우저이거나 간편비밀번호가 잠겼을 때. 실패 시 아이디 존재 여부를 노출하지 않는 공통 메시지, 5회 실패 시 10분 잠금. (b) 간편 로그인: 기기 등록 쿠키가 있는 브라우저에서 간편비밀번호 6자리만 입력. 서버가 해시를 비교하고 5회 실패 시 간편비밀번호를 잠근다. 두 방식 모두 성공 시 세션을 만들고 마지막 로그인 시각을 갱신한다. | 필수 |
| AUTH-03 | 세션 유지 / 만료 | 서버 세션 쿠키로 로그인 상태를 유지한다. 일정 시간(30분) 동작이 없으면 만료시키고, 만료 후 보호된 화면 요청은 로그인 화면으로 보낸다. 자연어 대화 맥락도 세션 단위로 묶는다. | 필수 |
| AUTH-04 | 본인 정보 접근 제어 | 로그인 필요 API는 공통 보호 장치(FastAPI 의존성 current_user)로 막는다. 미인증이면 401(LOGIN_REQUIRED), 간편비밀번호 미설정이면 403(PIN_SETUP_REQUIRED)을 돌려주고 프론트 라우터가 로그인·설정 화면으로 보낸다. 계좌·카드·거래·대화 기록의 모든 조회와 변경은 세션의 user_id로 필터링하며, URL에 타인의 식별자를 넣어도 404로 응답한다. | 필수 |
| AUTH-05 | 로그아웃 | 세션을 삭제하고 시작 화면으로 이동한다. 화면의 버튼과 자연어 요청("로그아웃 해줘") 양쪽에서 호출할 수 있다. | 필수 |
| AUTH-06 | 내 정보 조회 / 수정 | 이름, 생년월일, 휴대폰 번호, 가입일을 보여주고 휴대폰 번호만 수정할 수 있게 한다. 자연어 "내 정보 보여줘"의 이동 대상 화면이다. | 필수 |
| AUTH-07 | 비밀번호 변경 | 현재 비밀번호 확인 후 새 비밀번호로 변경한다. 새 비밀번호는 가입 시와 같은 규칙을 적용하고, 현재 비밀번호와 같으면 거부한다. 변경 후 다른 세션은 그대로 둔다(단일 기기 전제). 현재 비밀번호를 틀리면 로그인 실패와 같은 `failed_login_count`에 합산한다(5회 → 10분 잠금, 5.1.1과 동일). 요청의 `revokeOtherDevices`(기본 false)가 true이면 이 브라우저의 기기 등록만 남기고 나머지 등록을 해제한다(5.1.4). | 필수 |
| AUTH-08 | 간편비밀번호 | 첫 아이디·비밀번호 로그인 직후 숫자 6자리를 설정한다(필수, 건너뛰기 없음). 해시로 users에 저장하고 평문은 어디에도 남기지 않는다. 간편 로그인(AUTH-02b)과 2차 인증(이체 등 중요 동작 직전 확인 화면·함수) 양쪽에 같은 6자리를 쓴다. 내 정보 화면에서 현재 간편비밀번호 확인 후 변경할 수 있다. | 필수 |
| AUTH-09 | 기기 등록 쿠키 | 간편비밀번호 설정 완료 시 이 브라우저에 90일짜리 기기 쿠키를 발급하고 devices 테이블에 기록한다. 쿠키가 있는 브라우저에서만 간편 로그인 화면을 보여 준다. 내 정보 화면에서 "이 기기 등록 해제"로 쿠키와 레코드를 지울 수 있다. | 필수 |

구현 순서는 AUTH-01 → 02(a) → 03 → 04 → 05 순으로 하고, 이 다섯 가지가 끝난 뒤 08 → 09 → 02(b) → 06 → 07을 진행한다. 간편비밀번호 설정(08)과 기기 쿠키(09)가 있어야 간편 로그인(02b)을 만들 수 있다. AUTH-04는 다른 파트가 자기 화면을 만들 때부터 필요하므로, [TODO] 보호 장치의 사용법(6.1)을 먼저 공유한다.

### 3.2 이번에 구현하지 않는 것

| 항목 | 제외 이유 | 대체 방식 |
|---|---|---|
| 비밀번호 찾기 / 재설정 메일 | 메일 발송 인프라가 필요하고 평가 범위 밖 | 잊어버린 경우 테스트 계정을 새로 만든다 |
| 소셜 로그인(카카오·네이버·구글) | OAuth 앱 등록과 콜백 처리가 과제 핵심과 무관 | 아이디·비밀번호 로그인(AUTH-02a)과 간편 로그인(AUTH-02b)만 제공 |
| 휴대폰 본인인증, 실명 확인 | 외부 인증 서비스 연동 불가 | 번호만 입력받고, 필요하면 고정 인증번호 화면으로 흉내만 낸다 |
| 생체인증, 패턴 | 네이티브 앱 기능이라 웹에서 구현 범위 밖 | 간편비밀번호(AUTH-08)로 대체 |
| 보안 칩·서명 기반 기기 인증 | Secure Enclave, WebAuthn 같은 방식은 과제 범위 밖 | 서버가 발급한 기기 등록 쿠키(AUTH-09)로 대체. 쿠키 값은 무작위 토큰이며 서버에 해시로 저장 |
| 공동인증서, OTP | 실제 은행 보안 매체라 재현 불가 | 2차 인증은 간편비밀번호로 통일 |
| 다중 기기 세션 관리, 강제 로그아웃 | 단일 기기 사용 전제 | 세션 목록·강제 종료 기능은 두지 않는다. 기기 등록(AUTH-09)은 여러 브라우저를 허용하되, 관리 기능은 내 정보의 "이 기기 등록 해제"뿐이다(5.1.4) |
| 관리자 계정, 권한 등급 | 일반 사용자만 존재 | 모든 사용자는 동일 권한 |
| 회원 탈퇴 | 계좌·거래 데이터 정리 규칙이 필요해 범위가 커짐 | 이번 범위에서 제외 (확장 때 검토) |

### 4.2 검증 규칙

- **아이디 중복**: 입력 즉시 확인하지 않고, 해당 단계에서 "다음" 버튼을 눌렀을 때 서버에서 확인한다. 저장 직전(최종 제출)에도 한 번 더 확인해 동시 가입에 대비한다. 대소문자만 다른 아이디는 같은 아이디로 본다.
- **비밀번호 규칙**: 4.1의 규칙을 서버에서 검증한다. 브라우저의 입력 제한은 보조 수단으로만 쓰고, 최종 판단은 항상 서버가 한다. 비밀번호는 해시(bcrypt)로 저장하며 평문은 로그에도 남기지 않는다.
- **나이 제한**: 생년월일 기준 만 14세 이상만 가입할 수 있다. 실제 은행은 만 19세 미만에게 보호자 동의를 요구하지만, 이 프로젝트에서는 나이에 따른 상품 제한만 계좌 파트가 판단하도록 생년월일을 넘겨준다.
- **휴대폰 번호 중복**: 허용한다. 실제 본인인증이 없어 한 번호로 여러 테스트 계정을 만들 수 있어야 한다.
- **입력값 정리**: 모든 문자열은 앞뒤 공백을 제거하고, 아이디는 소문자로, 휴대폰 번호는 숫자만 남겨 저장한다.
- **검증 실패 시**: 해당 단계에 머물며 오류 메시지를 입력란 아래에 표시한다. 이미 입력한 다른 값은 유지한다.

### 4.3 가입 흐름

| 단계 | 화면 | 입력 | 다음 단계 조건 |
|---|---|---|---|
| 1 | 약관 동의 | 전체 동의 체크박스, 필수 2개, 선택 1개 | 필수 약관 모두 체크 |
| 2 | 아이디 | 아이디 | 형식 통과 + 중복 아님 |
| 3 | 비밀번호 | 비밀번호, 비밀번호 확인 | 규칙 통과 + 두 값 일치 |
| 4 | 기본 정보 | 이름, 생년월일, 휴대폰 번호 | 형식 통과 + 나이 조건 |
| 5 | 확인 및 완료 | 입력 내용 요약(비밀번호 제외), "가입하기" 버튼 | 서버 최종 검증 통과 |

- 각 단계 상단에 진행 표시(예: 2/5)를 두고, "이전" 버튼으로 돌아가면 입력값이 유지되도록 한다.
- 단계 사이의 입력값은 서버에 임시 저장하지 않고 브라우저(React 상태)에만 둔다. "다음"을 누를 때마다 `POST /api/auth/signup/validate` `{ step, data }`로 그 단계만 검증하고(1~4단계, 서버는 아무것도 저장하지 않는다, 아이디 중복 확인은 2단계), 5단계 "가입하기"에서 `POST /api/auth/signup`에 모든 필드를 보낸다. 서버는 1~4단계를 전부 다시 검증한 뒤 users에 저장하고 자동 로그인하며 `{ user, pinSetupRequired: true, next: "/auth/pin/setup" }`(201)로 응답한다. 최종 제출 전에는 서버에 아무것도 남지 않으므로 중간에 이탈해도 정리할 것이 없다(F-08). `/signup/2` 등으로 직접 들어오면(새로고침 포함) 입력값이 없으므로 1단계부터 다시 시작한다.
- 서버 렌더링 구현 시 단계별로 별도 URL(/signup/1 ~ /signup/5)을 두는 방식과, 한 페이지에서 단계를 전환하는 방식 중 하나를 택한다. 단순한 쪽은 단계별 URL이다.
- 가입 완료 후 이동할 화면: 자동 로그인 → 간편비밀번호 설정(S-07, 건너뛰기 없음) → 홈(S-04). 홈에서 "첫 계좌를 만들어 보세요" 안내를 띄워 계좌 개설 흐름으로 연결한다(계좌 파트와 협의).
- 간편비밀번호 설정은 가입 흐름의 일부가 아니라 "첫 로그인 직후 공통 단계"다. 가입으로 자동 로그인된 경우든, 시드 사용자가 처음 아이디·비밀번호로 로그인한 경우든 간편비밀번호가 없으면 S-07을 먼저 거친다(5.1.3).

## 5. 로그인 / 로그아웃

### 5.1 로그인

#### 5.1.0 방식 개요: 서버 검증형 간편비밀번호 + 기기 등록 쿠키

| 구분 | 내용 |
|---|---|
| 첫 로그인 | 아이디·비밀번호 (5.1.1) |
| 간편비밀번호 설정 | 첫 로그인 성공 직후 6자리 설정 → 해시로 users.simple_pin_hash에 저장 (5.1.3) |
| 기기 등록 | 설정 완료 시 이 브라우저에 90일짜리 기기 쿠키 발급, devices 테이블에 기록 (5.1.4) |
| 이후 로그인 | 기기 쿠키가 있는 브라우저 → 간편비밀번호 6자리만 입력 → 서버로 전송 → 해시 비교 → 세션 생성 (5.1.2) |
| 잠금 | 간편비밀번호 5회 실패 → 잠금. 아이디·비밀번호로 재인증한 뒤 간편비밀번호를 다시 설정해야 풀림 |
| 2차 인증 | 이체 등 중요 동작 직전에 같은 6자리를 재입력 (6장 R9, S-08) |

- "서버 검증형"이란 간편비밀번호를 브라우저에 저장하지 않고 매번 서버로 보내 해시와 비교한다는 뜻이다. 브라우저에는 사용자 식별이 가능한 기기 쿠키만 남는다.
- Secure Enclave 같은 보안 칩이나 공개키 서명(WebAuthn)은 쓰지 않는다. 그만큼 기기 쿠키가 유출되면 6자리 추측 공격에 노출되므로, 5회 잠금과 쿠키 HttpOnly 설정으로 보완한다.
- 실제 은행 앱과의 차이: 은행 앱은 기기 등록에 휴대폰 본인인증을 요구하지만, 이 프로젝트는 아이디·비밀번호 성공을 기기 등록 조건으로 삼는다.

#### 5.1.1 아이디·비밀번호 로그인 (S-03b)

- **언제 보이는가**: 기기 쿠키가 없거나 유효하지 않은 브라우저, 간편비밀번호가 잠긴 경우, 간편 로그인 화면에서 "다른 방법으로 로그인"을 누른 경우.
- **입력**: 아이디 + 비밀번호. 아이디는 소문자로 변환하고 앞뒤 공백을 제거한 뒤 조회한다.
- **처리 순서**:
  1. 아이디로 사용자 조회
  2. 잠금 상태(locked_until이 현재 시각 이후)면 잠금 메시지 표시 후 종료
  3. 비밀번호 해시 비교
  4. 실패: failed_login_count 1 증가, 5회 도달 시 locked_until을 10분 뒤로 설정
  5. 성공: failed_login_count 0, locked_until 비움, last_login_at 갱신, 세션 생성
  6. 간편비밀번호가 없거나(simple_pin_hash NULL) 잠겨 있으면 S-07 간편비밀번호 설정으로 이동(5.1.3). 있으면 이 브라우저를 기기로 등록할지 묻고(기본 "예") 홈으로 이동
- **성공 응답 (`POST /api/auth/login`)**: `{ user, pinSetupRequired, canRegisterDevice }`. `pinSetupRequired`가 true면 프론트가 S-07로 보낸다. `canRegisterDevice`는 간편비밀번호가 있고 이 브라우저가 이 사용자의 기기로 등록되어 있지 않을 때 true이며, 프론트는 true일 때만 6번의 기기 등록 질문을 띄운다.
- **없는 아이디**: 사용자가 없어도 더미 해시로 bcrypt 비교를 한 번 해서, 응답 시간 차이로 아이디 존재 여부가 드러나지 않게 한다.
- **잠금 자동 해제**: `locked_until`이 지난 뒤 처음 들어온 로그인 시도에서 `failed_login_count`를 0으로 되돌리고 잠금을 푼다. 비밀번호가 맞든 틀리든 해제 시점에 카운트가 새로 시작한다.
- **성공 시 이동 화면**: 홈(S-04). 로그인 전에 보호된 화면에 접근하려다 돌아온 경우(next 파라미터)에는 그 화면으로 복귀한다. next 값은 우리 사이트 내부 경로("/"로 시작)만 허용하고, 외부 URL이면 무시하고 홈으로 보낸다. 단, S-07을 거쳐야 하는 경우 next는 S-07 완료 후에 적용한다.
- **실패 시 메시지**: 아이디 없음과 비밀번호 틀림을 **구분하지 않는다**. 둘 다 "아이디 또는 비밀번호가 올바르지 않습니다."로 통일해 아이디 존재 여부가 드러나지 않게 한다. "(남은 시도 N회)"는 덧붙이지 않는다 (아이디 존재 여부가 드러나지 않게 하려는 것이고, 구현도 그렇다). 잠금에 걸릴 때만 해제 시각을 알려준다.
- **연속 실패 처리**: 5회 연속 실패 시 10분간 잠금. 잠금 중에는 올바른 비밀번호를 넣어도 "비밀번호를 5회 이상 잘못 입력해 10분간 로그인할 수 없습니다. (HH:MM 이후 가능)"을 표시한다. 잠금은 시간이 지나면 자동 해제되고, 해제 후 첫 성공 로그인에서 카운트가 0이 된다. 실제 은행은 영업점 방문 또는 본인인증으로 해제하지만, 이 프로젝트는 시간 경과 방식만 둔다.
- 이 실패·잠금 규칙은 아이디·비밀번호 로그인에만 적용된다. 간편 로그인의 실패·잠금은 5.1.2를 따르며, 두 카운터(failed_login_count, pin_failed_count)는 서로 독립이다.

#### 5.1.2 간편 로그인 (S-03a)

- **언제 보이는가**: /login 접근 시 유효한 기기 쿠키가 있으면 아이디·비밀번호 대신 이 화면을 먼저 보여 준다. 화면에는 등록된 사용자 이름 일부("김*나님")와 숫자 키패드, "다른 방법으로 로그인" 링크를 둔다.
- **처리 순서**:
  1. 기기 쿠키 값을 해시해 devices 테이블에서 조회. 없거나 만료(expires_at 경과)면 쿠키를 지우고 S-03b로 보낸다
  2. 해당 user의 간편비밀번호 잠금 상태(pin_locked_until)면 "간편비밀번호가 잠겼습니다. 아이디와 비밀번호로 로그인해 주세요" 표시 후 S-03b로 보낸다
  3. 입력된 6자리를 simple_pin_hash와 비교
  4. 실패: pin_failed_count 1 증가, 5회 도달 시 pin_locked_until 설정(해제 조건은 시간 경과가 아니라 5.1.3의 재설정). 남은 횟수를 표시한다("간편비밀번호가 틀렸습니다. 남은 횟수 3회")
  5. 성공: pin_failed_count 0, last_login_at 갱신, devices.last_used_at 갱신, 세션 생성, 홈(또는 next)으로 이동
- **입력 방식**: 숫자 키패드 화면에서 6자리가 모두 눌리면 자동 제출한다. 입력값은 POST 본문으로만 보내고 URL에 넣지 않는다.
- **구현 메모**: 화면은 먼저 `GET /api/auth/device`로 이 브라우저의 등록 여부를 묻는다. 응답은 `{ registered, name(마스킹), pinLocked, remaining }`이고, 쿠키가 위조·만료됐거나 사용자에게 간편비밀번호가 없으면 `registered: false`로 답하면서 쿠키를 지운다. `POST /api/auth/pin/login`도 기기가 유효하지 않으면 쿠키를 지우고 `DEVICE_INVALID`(401)로 응답한다. 로그인 성공 시 `devices.expires_at`을 90일 뒤로 늘리고 쿠키도 다시 내려준다. 6자리 숫자가 아닌 입력도 틀린 것으로 보고 횟수를 올린다(3.3 "구현과 다른 점").
- **키패드 배열**: 고정 배열(1~9, 0)을 쓴다. 무작위 배열은 이번 범위에서 하지 않는다 (구현도 고정 배열).

#### 5.1.3 간편비밀번호 설정·재설정 (S-07)

- **진입 조건**: (a) 가입 완료 직후 자동 로그인 상태, (b) 간편비밀번호가 없는 사용자의 첫 아이디·비밀번호 로그인 직후, (c) 간편비밀번호가 잠긴 사용자가 아이디·비밀번호로 로그인한 직후, (d) 내 정보 화면의 "간편비밀번호 변경"(이 경우 현재 6자리를 먼저 확인).
- **규칙**: 숫자 6자리. 같은 숫자 6개(111111), 연속 숫자(123456, 654321), 생년월일 6자리(YYMMDD)와 같으면 거부한다. 두 번 입력해 일치해야 한다.
- **처리**: 해시(bcrypt)로 simple_pin_hash에 저장, pin_set_at 기록, pin_failed_count 0, pin_locked_until 비움. 이어서 5.1.4의 기기 등록을 수행하고 홈(또는 next)으로 이동한다.
- **(a)(b)(c) 진입에서는 건너뛸 수 없다.** 설정을 끝내기 전에는 보호된 화면(S-04 이후)으로 이동할 수 없고, 접근하면 S-07로 되돌린다. 세션에는 "pin_setup_required" 표시를 두고 current_user 의존성이 이를 확인해 403을 돌려준다.
- 기존 간편비밀번호를 잊은 경우: 내 정보에서 "간편비밀번호 재설정" → 현재 비밀번호(아이디·비밀번호의 비밀번호) 확인 → 새 6자리 설정. 잠금 해제도 같은 경로다.
- **`POST /api/auth/pin/setup`의 세 가지 모드** (`pin`, `pinConfirm` + 아래):
  - 첫 설정·강제 설정: 세션에 `pin_setup_required`가 있을 때(진입 조건 a~c). 현재 값 확인 없이 설정한다.
  - 변경: `currentPin`으로 현재 6자리를 먼저 확인한다. 틀리면 `pin_failed_count`가 올라간다(5.1.2와 같은 카운터).
  - 재설정: `currentPassword`로 현재 비밀번호를 확인한다. (구현 현황은 3.3)
- **설정 뒤 기기 등록**: 어느 모드든 설정이 끝나면 이 브라우저를 기기로 다시 등록한다. 같은 브라우저의 기존 레코드는 revoked 처리하고 새 쿠키를 발급한다(5.1.4).
- **약한 번호 규칙(구현됨)**: 같은 숫자 6개, 오름·내림차순 연속 6자리(123456, 654321), 생년월일 YYMMDD와 같으면 `422`로 거부한다.

#### 5.1.4 기기 등록 쿠키

- **발급 시점**: 간편비밀번호 설정 완료 시 자동 발급. 이미 간편비밀번호가 있는 사용자가 새 브라우저에서 아이디·비밀번호로 로그인하면 "이 기기에서 간편 로그인을 사용할까요?"를 묻고 "예"일 때 발급한다.
- **쿠키 값**: 서버가 만든 무작위 토큰(32바이트 이상). 서버에는 토큰의 해시만 devices.token_hash에 저장한다. 쿠키 이름은 device_token, 유효기간 90일, HttpOnly, SameSite=Lax, 개발 환경에서는 Secure 끔. 세션 쿠키와 별개의 쿠키다.
- **검증**: 요청의 device_token을 해시해 devices에서 찾고, expires_at이 지나지 않았고 revoked_at이 NULL이면 유효하다. 쿠키 자체에는 user_id를 넣지 않는다(서버 조회로만 사용자를 알아낸다).
- **갱신**: 간편 로그인 성공 시 expires_at을 다시 90일 뒤로 연장한다(슬라이딩).
- **해제**: 내 정보 화면 "이 기기 등록 해제" → revoked_at 기록, 쿠키 삭제. 비밀번호 변경(AUTH-07) 시에는 다른 기기의 등록을 모두 해제할지 묻는다(기본 "아니오", 단일 기기 전제).
- **한 사용자당 기기 수**: 제한하지 않는다. 단, 같은 브라우저에서 다시 등록하면 기존 레코드를 revoked 처리하고 새로 만든다.
- **기기 쿠키와 세션 쿠키의 역할 구분**: 세션 쿠키는 "지금 로그인되어 있음"(30분), 기기 쿠키는 "이 브라우저는 간편 로그인 자격이 있음"(90일). 로그아웃은 세션 쿠키만 지운다.

#### 5.1.5 로그인 화면 공통 사항

- **이미 로그인된 상태에서 로그인 화면 접근**: S-03a·S-03b 모두 홈으로 바로 보낸다(7.2).
- **로그인 화면 구성**: S-03b는 아이디, 비밀번호, "로그인" 버튼, "회원가입" 링크. S-03a는 사용자 이름 일부, 6자리 입력 표시(●●●○○○), 숫자 키패드, "다른 방법으로 로그인" 링크. 아이디 저장 체크박스는 두지 않는다(기기 쿠키가 그 역할을 대신한다).
- **/login 진입 분기**: 유효한 기기 쿠키가 있으면 S-03a, 없으면 S-03b. /login/password로 직접 들어오면 쿠키와 무관하게 S-03b.

### 5.2 로그아웃

- **처리 방식**: POST 요청으로만 처리한다(GET 링크로 로그아웃되면 외부 링크 클릭만으로 로그아웃되는 문제가 있음). 서버 세션을 완전히 비우고(clear) 세션 쿠키를 만료시킨다. 자연어 대화 맥락도 세션에 있으므로 함께 사라진다.
- **호출 경로**: 홈·내 정보 화면의 로그아웃 버튼, 자연어 요청("로그아웃 해줘"). 자연어 경로에서는 "로그아웃할까요?" 확인 없이 바로 처리하고 결과만 알려준다(되돌리기 쉬운 동작이므로).
- **기기 쿠키는 유지한다**: 로그아웃은 세션만 끊는다. 같은 브라우저에서 다시 /login에 들어오면 간편 로그인 화면(S-03a)이 뜬다. 기기 등록까지 지우려면 내 정보의 "이 기기 등록 해제"를 쓴다(5.1.4).
- **로그아웃 후 이동 화면**: 시작 화면(S-01)으로 이동하며 "로그아웃되었습니다." 안내를 한 번 표시한다.
- **로그인하지 않은 상태에서 로그아웃 요청**: 오류 없이 시작 화면으로 보낸다.

### 5.3 세션

- **저장 방식**: Starlette SessionMiddleware(서명된 쿠키 세션, itsdangerous)를 쓴다. 토큰(JWT) 방식은 만료·무효화가 번거롭고 잠금·로그아웃 설계와 어긋나 쓰지 않는다. 별도 세션 테이블은 두지 않는다. React 프론트는 fetch에 `credentials: "include"`를 붙여 세션 쿠키를 보내고, 개발 중에는 Vite proxy로 /api를 백엔드에 전달해 같은 출처로 동작시킨다(공통.md 1장).
- **세션에 저장하는 값**: user_id, 로그인 시각, 로그인 방식(password / pin), 마지막 활동 시각, 자연어 대화 맥락(최근 N턴), 간편비밀번호 설정 필요 표시(pin_setup_required), 2차 인증 통과 시각(pin_verified_at). 가입 진행 중 입력값은 서버 세션에 두지 않는다(4.3).
  - 구현에서 실제로 쓰는 키: `user_id`, `login_at`, `login_method`, `last_active`, `pin_setup_required`, `pin_verified_at`. 30분 만료 규칙은 `last_active`로 판단한다.
- **기기 쿠키는 세션과 별개**: 기기 쿠키(device_token)는 세션에 넣지 않고 독립 쿠키로 둔다. 세션이 만료되어도 기기 쿠키는 남아 간편 로그인으로 바로 재진입할 수 있다(5.1.4).
- **쿠키 설정**: HttpOnly 켬, SameSite=Lax, 개발 환경에서는 Secure 끔(배포 시 켬). 세션 서명 키는 코드에 넣지 않고 환경 변수(.env)로 읽는다.
  - 세션 쿠키 이름은 `aim_session`(서명됨, 브라우저 세션 수명). `https_only`는 개발 중 꺼 둔다.
  - 서명 키 환경 변수는 `SESSION_SECRET`이다. 개발용 기본값이 있으므로 배포 전에 길고 무작위인 값으로 바꾼다(`backend/.env.example`).
  - 기기 쿠키 `device_token`: HttpOnly, SameSite=Lax, 90일 슬라이딩, 개발 환경에서는 Secure 끔(5.1.4).
  - CORS는 `http://localhost:5173`(과 `127.0.0.1:5173`)에서 오는 요청을 자격 증명 포함으로 허용한다.
- **만료 시간**: 마지막 활동 기준 30분. 요청이 올 때마다 마지막 활동 시각을 갱신한다(슬라이딩 방식). 실제 은행 앱은 5~10분이지만, 시연 중 끊기지 않도록 30분으로 둔다.
- **만료 후 요청 시 동작**:
  - 화면 요청: 세션을 비우고 로그인 화면으로 보내며 "로그인 시간이 만료되었습니다. 다시 로그인해 주세요." 안내. 원래 요청 경로를 next로 넘겨 로그인 후 복귀한다.
  - 자연어 요청: 같은 안내와 함께 로그인 화면 링크를 응답으로 돌려준다. 대화 맥락은 세션과 함께 사라진 것으로 본다.
  - 폼 제출(POST) 중 만료: 입력값은 복구하지 않고 로그인 화면으로 보낸다.
- **로그인 시 세션 재생성**: 로그인 성공 시 기존 세션 값을 비우고 새로 만들어 세션 고정 공격을 막는다.
- **동시 로그인**: 같은 계정으로 다른 브라우저에서 로그인해도 막지 않는다(3.2의 단일 기기 전제대로 관리 기능은 두지 않음).

### 5.4 2차 인증 확인 API (S-08)

- **목적**: 이체, 예적금 해지, 카드 동작 직전에 간편비밀번호 6자리를 다시 확인한다(R9). 규칙의 원본은 공통.md 4장이다.
- **API**: `POST /api/auth/pin/verify` `{ "pin": "135792" }`. 업무 API는 같은 서버의 함수 `pin_verified(request)`로 통과 여부를 확인한다.
- **통과 기록**: 통과하면 세션 키 `pin_verified_at`에 시각을 기록한다. 이후 5분 동안은 여러 번 실행해도 다시 묻지 않는다.
- **미통과 시**: 확인하지 않았거나 5분이 지났는데 업무 API가 호출되면 `403 PIN_VERIFICATION_REQUIRED`로 응답한다.

| HTTP | code | 내용 |
|:---:|---|---|
| 200 | - | 통과. `{ "verified": true, "validForSeconds": 300 }` |
| 400 | `VALIDATION_FAILED` | 6자리 숫자가 아님 (횟수에 넣지 않음) |
| 403 | `PIN_MISMATCH` | 틀림. `remainingAttempts` |
| 403 | `PIN_SETUP_REQUIRED` | 간편비밀번호 미설정 |
| 423 | `PIN_LOCKED` | 5회 연속 실패로 잠김 |

- **횟수·잠금**: 틀린 횟수는 5.1.2와 같은 `pin_failed_count`다. 5번째로 틀린 요청에서 423으로 응답하고 `pin_locked_until`을 설정한다. 잠금은 S-07 재설정으로만 풀린다.
- **보안**: 틀린 6자리는 어디에도 기록하지 않는다.
- **S-08 구현 형태**: 페이지 `/auth/pin/verify?next=<내부 경로>&desc=<설명>`이다. `desc`는 화면에 보여 줄 동작 설명이다. 통과하면 `pin_verified_at`이 기록되고 `next`로 이동한다(replace). 취소는 이전 화면으로 돌아간다. `PIN_LOCKED`로 응답하면 로그인 상태를 새로 읽고 `/login`으로 보낸다. `next`는 R2와 같은 `safeNext` 규칙을 따른다.
- **`PinKeypad` 컴포넌트**: 6자리 숫자 키패드(●●●○○○ 표시)는 재사용 컴포넌트 `frontend/src/auth/PinKeypad.tsx`이고, 6자리가 모두 눌리면 자동으로 `onComplete`를 부른다. 다단계 폼처럼 페이지를 벗어나면 입력 상태가 사라지는 흐름(다른 파트)은 페이지 이동 대신 자기 다이얼로그 안에서 `PinKeypad`를 쓰고 `POST /api/auth/pin/verify`를 직접 호출해도 된다(공통.md 4장).

## 6. 접근 제어 규칙 (공통 규칙, 전원 적용)

파트가 함께 지키는 규칙의 요약은 공통.md 3장이다. 두 문서가 다르면 공통.md가 우선이다.

| 규칙 | 내용 |
|---|---|
| R1 | 로그인 없이 접근 가능한 화면은 시작(S-01), 회원가입(S-02), 로그인(S-03a/b), 상품 안내(금리·가입 조건 소개, 계좌 파트), 정적 파일뿐이다. 그 외 모든 화면과 API는 로그인이 필요하다. |
| R2 | 로그인 필요 화면에 미인증 접근 시 로그인 화면으로 보내고, 로그인 후 원래 화면으로 복귀한다(next 파라미터, 내부 경로만 허용). `next`는 `/`로 시작해야 하고 `//`로 시작하거나 `://`를 포함하면 안 되며 `/login`·`/signup`을 가리켜도 안 된다(프론트 `safeNext`). 조건에 어긋나면 무시하고 홈으로 보낸다. POST 요청이었다면 복귀하지 않고 홈으로 보낸다. |
| R3 | 모든 데이터 조회·변경은 세션의 user_id로 필터링한다. 쿼리에 user_id 조건이 빠진 조회는 버그로 본다. 폼이나 URL로 넘어온 user_id 값은 절대 신뢰하지 않고 세션 값만 쓴다. |
| R4 | URL이나 폼에 타인의 계좌번호·카드번호·거래 ID를 넣어도 조회·변경되지 않아야 한다. 존재하지 않는 것과 똑같이 404로 응답해 타인 데이터의 존재 여부도 노출하지 않는다. |
| R5 | 보호 장치는 한 가지로 통일한다. 로그인 필요 API마다 FastAPI 의존성 `user: User = Depends(current_user)`를 붙이고, 각자 자기 파트 라우터에 빠짐없이 적용한다. 보호 여부는 7장 화면 목록의 "인증 필요" 열을 기준으로 한다. 미인증은 401(LOGIN_REQUIRED), 간편비밀번호 미설정은 403(PIN_SETUP_REQUIRED, R10)으로 응답하고, 화면 이동은 프론트 라우터가 맡는다. |
| R6 | 로그인한 사용자 정보는 요청마다 세션의 user_id로 DB에서 다시 읽어 쓴다(current_user 의존성이 조회해 돌려준다). 이름·잔액 등을 세션에 캐시하지 않아 값이 바뀌어도 바로 반영된다. |
| R7 | 상태를 바꾸는 요청(가입, 로그인, 로그아웃, 이체, 개설 등)은 반드시 POST로 받고, GET으로는 조회만 한다. CSRF는 SameSite=Lax 쿠키와 `Origin` 헤더 확인으로 막는다. `Origin`이 없는 요청은 통과시키고 폼 토큰은 쓰지 않는다(공통.md 3장). |
| R8 | 자연어 요청으로 실행되는 기능도 같은 규칙을 따른다. 자연어 처리기는 세션의 user_id를 받아 기능 함수를 호출하며, 사용자가 문장 안에 다른 사람의 이름이나 계좌를 넣어도 본인 데이터 범위 안에서만 동작한다. |
| R9 | 이체, 예적금 해지, 카드 동작(카드 일시정지·정지 해제·분실 신고·신청·해지) 같은 중요 동작은 실행 직전에 간편비밀번호 확인(S-08)을 거친다(공통.md 4장). 통과 시각을 세션(pin_verified_at)에 기록하고 통과 후 5분 동안은 다시 묻지 않는다. 계좌 파트는 pin_verified(request) 함수로 확인하거나 S-08로 보낸다. 간편비밀번호 입력 실패는 5.1.2의 pin_failed_count를 공유한다(5회 실패 시 간편 로그인도 함께 잠김). |
| R10 | 간편비밀번호를 아직 설정하지 않은 세션(pin_setup_required)은 S-07 외의 보호 화면에 접근할 수 없다. current_user 의존성이 이 표시를 확인해 403(code: PIN_SETUP_REQUIRED)을 돌려주고, 프론트가 S-07로 보낸다. 간편비밀번호 설정 API(/api/auth/pin/setup)만 이 검사를 건너뛴다. |

### 6.1 적용 방식 예시 (전원 공통)

```python
# backend/app/auth/deps.py  (회원·인증 파트가 제공)
def current_user(request: Request, db: Session = Depends(get_db)) -> User:
    user_id = request.session.get("user_id")
    if not user_id:
        raise HTTPException(401, {"code": "LOGIN_REQUIRED"})            # R2
    # 마지막 활동 시각 확인·갱신 (30분 슬라이딩, 5.3). 만료면 세션 비우고 401(code: SESSION_EXPIRED)
    if request.session.get("pin_setup_required"):
        raise HTTPException(403, {"code": "PIN_SETUP_REQUIRED"})        # R10
    user = db.get(User, user_id)                                        # R6: 요청마다 DB에서 읽음
    if user is None:
        request.session.clear()
        raise HTTPException(401, {"code": "LOGIN_REQUIRED"})
    return user

# backend/app/accounts/router.py  (모든 파트가 같은 방식으로 사용)
@router.get("/api/accounts")
def account_list(user: User = Depends(current_user), db: Session = Depends(get_db)):   # R5
    return db.query(Account).filter_by(user_id=user.id).all()                            # R3

@router.get("/api/accounts/{account_id}")
def account_detail(account_id: int, user: User = Depends(current_user), db: Session = Depends(get_db)):
    account = db.query(Account).filter_by(id=account_id, user_id=user.id).first()        # R3
    if account is None:
        raise HTTPException(404)                                                          # R4
    return account
```

- current_user 의존성과 get_db는 회원·인증 파트가 제공하고, 다른 파트는 가져다 쓴다. user_id를 요청 본문이나 쿼리에서 받는 API는 만들지 않는다.
- 프론트는 공통 fetch 래퍼에서 401이면 /login으로(원래 경로를 state에 담아 복귀), 403(PIN_SETUP_REQUIRED)이면 S-07로 보낸다. 서버는 리다이렉트하지 않는다.
- 오류 응답 형식은 `{ code, message, details? }`로 통일하고, 모든 `code`는 대문자 SNAKE_CASE다(공통.md 5장).
- 각자 구현 완료 후 "타인 계좌 URL 직접 입력" 테스트(F-06)를 전원이 돌려 R4를 확인한다.

- 서버가 리다이렉트하던 동작(미인증 → 로그인, 로그인 상태에서 /login → 홈, 미설정 → S-07)은 모두 프론트 라우터가 401/403 응답과 로그인 상태를 보고 처리한다(6.1).
- 모바일 레이아웃: 전 화면 공통으로 폭 420px 고정, 하단 탭 바는 로그인 후 화면(S-04, S-05, S-06, S-07 변경 모드)에만 표시한다. S-07 첫 설정·재설정(/auth/pin/setup)과 S-08 2차 인증은 다른 화면으로 이동하면 안 되는 단계이므로 탭 바를 숨긴다(R10).
- 하단 탭 "내 정보"는 회원·인증 파트가, 나머지 탭은 각 파트가 담당한다.
- 구현된 인증 라우트: `/login`, `/login/password`, `/signup/:step`, `/auth/pin/setup`, `/auth/pin/verify`, `/auth/reset`, `/me`, `/me/password`(S-06), `/me/pin`(S-07 변경). 화면 가드는 `RequireAuth`(보호 화면)와 `PublicOnly`(로그인·가입 화면)다.

### 7.3 API 목록

구현된 인증 API 전체다. 요청·응답 필드는 구현 기준이고, 오류 코드는 표준 이름으로 적는다(구현의 실제 이름은 3.3). 오류 코드 전체는 `../common/오류코드.md`에 있다. "인증"의 뜻은 로그인 = `current_user`(401/403 검사 포함), 세션 = `current_user_any`(간편비밀번호 미설정이어도 통과), 없음 = 세션 불필요다.

| 메서드·경로 | 인증 | 요청 본문 | 성공 응답 | 오류 코드 |
|---|---|---|---|---|
| `POST /api/auth/signup/validate` | 없음 | `step`(1~4), `data`(그 단계의 입력 필드) | `{ ok: true }` | `VALIDATION_FAILED`(단계 번호가 잘못돼도 같은 코드) |
| `POST /api/auth/signup` | 없음 | `termsService`, `termsPrivacy`, `marketing`, `loginId`, `password`, `passwordConfirm`, `name`, `birthDate`, `phone` | 201 `{ user, pinSetupRequired: true, next: "/auth/pin/setup" }` | `VALIDATION_FAILED` |
| `POST /api/auth/login` | 없음 | `loginId`, `password` | `{ user, pinSetupRequired, canRegisterDevice }` | `INVALID_CREDENTIALS` 401, `LOGIN_LOCKED` 423(`details.until`) |
| `GET /api/auth/device` | 없음 | - | `{ registered, name(마스킹), pinLocked, remaining }`. 위조·만료 쿠키는 삭제 | - |
| `POST /api/auth/pin/login` | 없음(기기 쿠키) | `pin` | `{ user, pinSetupRequired: false }` | `DEVICE_INVALID` 401, `PIN_MISMATCH` 401(`details.remainingAttempts`), `PIN_LOCKED` 423 |
| `POST /api/auth/device/register` | 로그인 | - | `{ ok: true }` | `LOGIN_REQUIRED`, `SESSION_EXPIRED`, `PIN_SETUP_REQUIRED` |
| `POST /api/auth/device/revoke` | 로그인 | - | `{ ok: true }`. 이 브라우저의 등록 해제, 쿠키 삭제 | `LOGIN_REQUIRED`, `SESSION_EXPIRED`, `PIN_SETUP_REQUIRED` |
| `POST /api/auth/pin/setup` | 세션 | `pin`, `pinConfirm`, 변경이면 `currentPin`, 재설정이면 `currentPassword` | `{ ok: true }`. 끝나면 이 브라우저를 기기로 (재)등록 | `LOGIN_REQUIRED`, `SESSION_EXPIRED`, `PIN_MISMATCH` 403, `PIN_LOCKED` 423, `CURRENT_PASSWORD_INVALID` 403, `VALIDATION_FAILED` |
| `POST /api/auth/pin/verify` | 로그인 | `pin` | `{ verified: true, validForSeconds: 300 }` | `PIN_SETUP_REQUIRED`, `PIN_MISMATCH` 403, `PIN_LOCKED` 423, `VALIDATION_FAILED` |
| `POST /api/auth/password/change` | 로그인 | `currentPassword`, `newPassword`, `newPasswordConfirm`, `revokeOtherDevices`(기본 false) | `{ ok: true }` | `CURRENT_PASSWORD_INVALID` 403, `LOGIN_LOCKED` 423, `VALIDATION_FAILED` |
| `POST /api/auth/logout` | 없음 | - | `{ ok: true }`. POST만 받고(GET은 405) 로그인하지 않았어도 항상 200 | - |
| `GET /api/auth/session` | 없음 | - | `{ authenticated, expired?, pinSetupRequired, user }`. 화면이 시작할 때 부른다 | - |
| `GET /api/me` | 로그인 | - | `{ user: { id, loginId, name, birthDate, phone, createdAt, lastLoginAt }, deviceRegistered, deviceName }` | `LOGIN_REQUIRED`, `SESSION_EXPIRED`, `PIN_SETUP_REQUIRED` |

- `user`는 가입·로그인 응답에서 `{ id, loginId, name }`이다.
- `VALIDATION_FAILED`의 필드별 reason: loginId `INVALID_FORMAT`/`ALREADY_TAKEN`, password `PASSWORD_RULE`/`CONTAINS_LOGIN_ID`/`SAME_AS_CURRENT`, passwordConfirm·newPasswordConfirm·pinConfirm `MISMATCH`, name·birthDate·phone `INVALID_FORMAT`, birthDate `UNDER_AGE`, terms `MUST_BE_TRUE`, pin `INVALID_FORMAT`/`PIN_TOO_SIMPLE`.
- 다른 파트가 쓰는 함수(`backend/app/auth/deps.py`, `router.py`):
  - `current_user`: 로그인 필요 API의 보호 장치(6.1).
  - `current_user_any`: `current_user`에서 간편비밀번호 설정 검사(R10)만 건너뛴다. 설정 전에도 필요한 API용이고, 현재는 `/api/auth/pin/setup`이 쓴다.
  - `pin_verified(request)`: 세션의 `pin_verified_at`이 5분 안이면 True(5.4).
  - `get_age(user)`: 생년월일 기준 만 나이(`get_age(user, today=None)`).

## 8. DB 설계 (users)

### 8.1 users 테이블

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | BIGINT | PK, GENERATED BY DEFAULT AS IDENTITY | 다른 모든 테이블이 참조하는 사용자 식별자. 시드가 id 1~4를 직접 넣으므로 ALWAYS가 아니라 BY DEFAULT이고, 시드 뒤에 시퀀스를 맞춘다(`setval`) |
| login_id | VARCHAR(20) | UNIQUE, NOT NULL | 아이디. 소문자로 정규화해 저장 (4.1) |
| password_hash | TEXT | NOT NULL | bcrypt 해시(rounds 10). 평문 저장 금지 |
| name | VARCHAR(30) | NOT NULL | 이름 |
| birth_date | DATE | NOT NULL | 생년월일. 나이 제한(4.2)과 상품 가입 조건(계좌 파트) 판단에 사용 |
| phone | VARCHAR(11) | NOT NULL | 숫자만 저장(예: 01012345678). 중복 허용 |
| marketing_agree | BOOLEAN | NOT NULL, DEFAULT false | 선택 약관 동의 여부 |
| simple_pin_hash | TEXT | NULL 허용 | 간편비밀번호(6자리) bcrypt 해시(rounds 10). 간편 로그인과 2차 인증에 공용. 미설정이면 NULL |
| pin_set_at | TIMESTAMPTZ | NULL 허용 | 간편비밀번호 설정·변경 시각 |
| pin_failed_count | INTEGER | DEFAULT 0 | 간편비밀번호 연속 실패 횟수(간편 로그인·2차 인증 공유). 성공 시 0 |
| pin_locked_until | TIMESTAMPTZ | NULL 허용 | 간편비밀번호 잠금 표시. 시간 경과로 풀리지 않고 재설정(5.1.3)으로만 해제. 잠금 시 먼 미래 값(예: 9999-12-31)을 넣는다 |
| failed_login_count | INTEGER | DEFAULT 0 | 아이디·비밀번호 연속 실패 횟수. 성공 시 0 |
| locked_until | TIMESTAMPTZ | NULL 허용 | 아이디·비밀번호 잠금 해제 시각. NULL 또는 과거면 잠금 아님 |
| created_at | TIMESTAMPTZ | NOT NULL, DEFAULT now() | 가입일시 |
| last_login_at | TIMESTAMPTZ | NULL 허용 | 마지막 로그인 성공 시각 |

- 주민등록번호 뒷자리, 비밀번호 평문, 간편비밀번호 평문, 기기 토큰 원문은 어떤 형태로도 저장하지 않는다.
- 이메일은 받지 않으므로 컬럼을 두지 않는다. 나중에 필요하면 NULL 허용 컬럼으로 추가한다.
- PostgreSQL 기준 타입이다(공통.md 6장). 시각은 모두 TIMESTAMPTZ(UTC 저장, 표시 시 KST 변환), 불리언은 BOOLEAN, 식별자는 BIGINT IDENTITY. 스키마는 Alembic 마이그레이션으로 관리한다.

### 8.1.1 devices 테이블 (기기 등록 쿠키)

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| id | BIGINT | PK, GENERATED ALWAYS AS IDENTITY | 시드가 id를 넣지 않으므로 users와 달리 ALWAYS |
| user_id | BIGINT | FK users.id, NOT NULL | 이 기기로 간편 로그인할 사용자 |
| token_hash | TEXT | UNIQUE, NOT NULL | 기기 쿠키 값의 SHA-256 해시(16진수 문자열). 쿠키 값은 `secrets.token_urlsafe(32)`로 만든 무작위 토큰이고 원문은 저장하지 않는다 |
| device_name | TEXT | | User-Agent에서 뽑은 표시용 이름(예: "Chrome · Windows"). 내 정보 화면 표시용 |
| created_at | TIMESTAMPTZ | NOT NULL, DEFAULT now() | 등록 시각 |
| last_used_at | TIMESTAMPTZ | NULL 허용 | 마지막 간편 로그인 성공 시각 |
| expires_at | TIMESTAMPTZ | NOT NULL | 만료 시각. 등록·간편 로그인 성공 시 90일 뒤로 갱신 |
| revoked_at | TIMESTAMPTZ | NULL 허용 | 등록 해제 시각. NULL이 아니면 무효 |

- 쿠키 → 사용자 조회는 token_hash 단일 조회로 끝난다. 쿠키에 user_id를 넣지 않는다.
- 한 사용자가 여러 기기를 가질 수 있다(N:1). 같은 브라우저에서 재등록하면 이전 레코드는 revoked 처리한다.
- 만료·해제된 레코드는 지우지 않고 남겨 두어 "최근 로그인 기기" 표시에 쓸 수 있다(선택).

### 8.2 다른 테이블과의 관계 (DB 담당에게 전달)

| 테이블 | 연결 | 규칙 |
|---|---|---|
| devices | devices.user_id -> users.id (N:1) | 기기 등록 쿠키(8.1.1). 인증 파트만 읽고 쓴다 |
| accounts | accounts.user_id -> users.id (N:1) | 한 사용자가 여러 계좌. 계좌 조회·변경은 항상 user_id 조건 포함 (R3) |
| cards | cards.user_id -> users.id (N:1), 필요 시 cards.account_id -> accounts.id | 카드 소유자는 user_id로 직접 확인한다. 연결 계좌를 통해 간접 확인하지 않는다 |
| transactions | transactions.account_id -> accounts.id | user와 직접 연결하지 않고 계좌를 통해 연결. 조회 시 accounts와 조인해 user_id를 확인 |
| chat_sessions, chat_messages | chat_sessions.user_id -> users.id (N:1), chat_messages.session_id -> chat_sessions.id | 자연어 대화 기록 (구현된 가계부 대화가 쓰는 테이블). 로그인 세션별 맥락은 chat_sessions로 구분 |
| 추가 기능 테이블 (적금, 가계부 등) | *.user_id -> users.id | 사용자 소유 데이터는 예외 없이 user_id 컬럼을 가진다 |

- 외래키에는 ON DELETE 규칙을 두지 않는다(회원 탈퇴 미구현, 3.2).
- 시드 데이터 생성 순서: users → accounts → cards → transactions. 시드 사용자 4명(4.4, 공통.md 7장)의 id는 1~4로 고정해 다른 파트의 시드 스크립트가 참조할 수 있게 한다.

### 8.3 세션 저장

- **방식**: 프레임워크 기본 서버 세션(서명된 쿠키)을 사용한다. 5.3에서 정한 대로 세션에는 user_id와 활동 시각, 대화 맥락 등만 담는다.
- **테이블 필요 여부**: 세션 테이블은 두지 않는다. 쿠키 세션으로 충분하고, 강제 로그아웃이나 다중 기기 관리를 하지 않기 때문이다.
- **대화 맥락 저장 위치**: 세션에는 최근 5턴 정도만 두고, 전체 기록은 chat_messages에 남긴다. 세션 쿠키는 용량 제한(약 4KB)이 있으므로 긴 대화를 세션에 넣지 않는다.
- **로그인 실패 기록**: 세션이 아니라 users 테이블(failed_login_count, locked_until, pin_failed_count, pin_locked_until)에 둔다. 브라우저를 바꿔도 잠금이 유지되어야 하기 때문이다.
- **기기 등록 기록**: devices 테이블(8.1.1). 세션과 무관하게 90일 유지되므로 DB에 둔다.

| auth.lock_status | "왜 로그인이 안 돼?", "계정 잠겼어?", "간편비밀번호가 잠겼어" | 미인증 상태에서만 의미 있음. 잠금 정책 안내(비밀번호 5회 → 10분, 간편비밀번호 5회 → 아이디·비밀번호로 재인증 후 재설정)와 /login 링크. 특정 아이디의 잠금 여부는 알려주지 않는다 | 없음 |
| auth.faq (RAG) | "비밀번호 규칙이 뭐야?", "만 14세 미만도 가입돼?" | RAG로 이 기획서·약관 문서에서 검색해 답변 | 없음 |

- 비밀번호, 간편비밀번호 같은 비밀값은 어떤 의도에서도 채팅 입력으로 받지 않고 화면으로 보낸다. chat_messages에 남기 때문이다.
- 의도 이름(auth.*)은 자연어 담당의 명명 규칙에 맞춰 바꾼다.
- 인증 파트는 직접 실행 의도에 대응하는 함수(logout(user), get_my_info(user), update_phone(user, phone), revoke_device(user, device_token))를 제공하고, 자연어 처리기가 세션의 user를 넘겨 호출한다 (R8). 화면 링크로 처리하는 의도(auth.change_password, auth.set_pin 등)는 함수 없이 URL만 돌려준다.

### 9.2 미인증 상태의 요청 처리

- **로그인 안 한 상태에서 "내 계좌 보여줘" 입력 시**: 기능을 실행하지 않고 "로그인 후 이용할 수 있어요. [로그인하기]" 응답과 /login 링크(S-03a 또는 S-03b)를 준다. 로그인 후 원래 요청을 자동 재실행할지는 하지 않는다(요청 문장을 세션에 보관해야 하고 복잡해짐). 대신 로그인 후 홈의 입력창에 안내만 띄운다.
- **미인증 상태에서 허용하는 의도**: auth.signup_guide, auth.login_guide, auth.lock_status, auth.faq(상품·규칙 안내 RAG). 그 외 모든 의도는 로그인 안내로 응답한다.
- **미인증 상태에서 자연어 입력창을 보여줄지**: 시작 화면(S-01)에 입력창을 두지 않는다. 자연어 입력창은 홈(S-04) 이후에만 있으므로, 미인증 요청은 사실상 세션 만료 경우에만 발생한다. 단, 자연어 담당이 시작 화면에도 상품 안내용 입력창을 원하면 위 허용 의도 목록으로 제한한다.
- **세션 만료 후 자연어 요청 시**: "로그인 시간이 만료되었습니다. 다시 로그인해 주세요. [로그인하기]" 응답. 세션이 사라졌으므로 대화 맥락도 초기화된 것으로 안내한다.
- **의도 판별 전 인증 확인 순서**: 자연어 처리기는 의도 분류보다 먼저 세션의 user를 확인하고, 미인증이면 허용 의도 목록만 분류 대상으로 한다. 이렇게 하면 미인증 상태에서 LLM이 계좌 조회 함수를 호출하는 일이 구조적으로 막힌다.
