# 대출 서비스 종합 정리

> 기획서(이 폴더의 `Loan_Service_main.md` 등)와 프로토타입 구현명세의 규칙을 **실행 가능한 파이썬 코드 + DB**로 옮긴 결과물이고, 서버(`backend/app/loan/`)에 통합되어 있습니다.
> 모든 금리·한도·기준값은 **예시값**이며 실제 상품 조건이 아닙니다.
> 회원(`users`)·계좌(`accounts`, `transactions`)는 서버의 같은 DB에 있고, 대출 테이블은 그 id를 FK 없이 값으로만 참조합니다(공통.md 6장). 로그인·카드 연동 칸은 아직 비어 있습니다.

## 2. 실행 방법

서버에 통합되어 있습니다. `alembic upgrade head`로 대출 테이블을 만든 뒤 서버를 켜면 기준 데이터가 들어갑니다(시연 회원 user1에게 대출 2건도 만듭니다).

```bash
cd backend && uvicorn app.main:app --reload
```

콘솔로 흐름을 눌러 보려면(회원 없이 실행):

```bash
cd backend && python -m app.loan
```

```bash
cd backend && python -m app.loan --auto
```

테스트: 단위·계좌 연동 테스트(`test_loan.py`)는 전용 스키마(`loan_test`)에서 돌아 개발 DB(5432)를 그대로 써도 된다. API 흐름 테스트(`test_loan_api.py`)는 DB를 바꾸므로 같은 서버의 시험 DB `aimbank_loantest`를 따로 만들어 마이그레이션한 뒤 돌린다(명령은 테스트 파일 머리말).

## 3. 업무 흐름 (코드 기준)

```
상품 선택 ─ (정부) G01 자격 사전확인
   │
   ▼
C02 약관·동의 ──(필수 미동의)──▶ 중단
   │                       (대환) R03 기존 대출 조회 → R04 대환 자격 → 대상 선택
   ▼
C03 고객정보·적합성 ──(부적합)──▶ 조정 안내 → 고객 확인 시에만 진행
   │   (정부) 소득·자산 요건 / (기관A) 보증기관 선택 / (기관B) 협약기관·재직 확인
   ▼
C04 증빙 제출 (파일 검사·자동연동) → C05 7단계 심사(결격→소득→신용→DSR→담보→한도→판정)
   │                                   └ 거절 / 서류 보완 / 승인 / 조건부 승인
   ▼
C06 권장 상품 3안 (고객 비용 기준 순위 + LLM 사유 + V1~V9 검증)   (대환) R09 유불리 비교
   ▼
C07 조건 확정 → C08 금리 산정(우대) → C09 설명서·이해 확인 퀴즈 → C10 약정(전자서명 자리)
   ▼
C11 담보·보증 설정 → C12 실행(멱등 키) / (대환) 사가: 견적→실행 보류→상환 송금→완제 확인, 실패 시 보상
   ▼
C13 완료 → 대출 계좌 개설 → 대출관리(M01 스케줄, M05 중도상환, M06 금리인하, M07 철회, 기간연장, 증명서)
```

신청서 상태는 `loan/state_machine.py`의 허용 목록으로만 바뀝니다(예: `DRAFT → CONSENTED → PROFILED → DOCS_SUBMITTED → UNDER_REVIEW → APPROVED → TERMS_SET → PRICED → EXPLAINED → CONTRACTED → (COLLATERAL_SET) → DISBURSED → COMPLETED`). 순서를 건너뛰면 `InvalidTransition`으로 막히고, 모든 이동은 `application_status_history`와 감사 로그에 남습니다.

## 4. DB 설계

### 4.1 작성 규칙 (팀 공통 `docs/db/db-design.md` 준수)

- 금액 `BIGINT`(원), 금리 `NUMERIC(6,4)`(연 %), enum은 `VARCHAR + CHECK`, JSON은 `JSONB`
- 공통 `audit_log`(전 도메인 공용)와 이름이 겹치지 않도록 대출의 해시 체인 감사 로그는 `loan_audit_log`다
- ID는 `VARCHAR(40)` 접두어+ULID (예: `lap_01J…`), 계약 번호는 업무 번호 `LA-2026-NNNNNN`(대환 `RA-…`), UNIQUE
- 같은 영역 안은 FK, **다른 서비스(회원·로그인·은행·카드)는 FK 없는 논리 참조 빈 칸**(NULL 허용, `-- @ext` 표시)
- 민감값은 원문 저장 금지: 계좌번호·사번은 마스킹본 + HMAC 해시만, 감사 로그는 내용 해시만
- `schema.sql`의 `-- @domain`, `-- @ext` 태그를 `erd/make_erd.py`가 읽어 ERD를 다시 그림 → 스키마를 고치면 ERD 재생성만 하면 됨

### 4.3 다른 파트와 연결 지점 (논리 참조)

| 연결 파트 | 대출 쪽 칸 (테이블.컬럼) | 현재 상태 |
|---|---|---|
| 회원 (`users.id`, BIGINT) | loan_application.user_id, loan_account.user_id, inquiry_cache.user_id, notification.user_id, household_info.spouse_user_id | 신청 시작 때 세션의 `user_id`를 채움(요청 본문의 값은 쓰지 않음). `spouse_user_id`는 비어 있음 |
| 로그인·인증 (`auth_session`, `e_sign`) | loan_application.auth_ref, consent_record.auth_ref, contract.signature_ref | `login:<세션 로그인 시각>`, 약정 때 5분 안에 간편비밀번호를 확인했으면 `pin:<확인 시각>`(아니면 비어 있음). 전자서명 서비스는 없다 |
| 계좌 (`accounts`, `transactions`, 둘 다 BIGINT id) | disbursement.account_id, disbursement.account_txn_ref, loan_terms.auto_debit_account_id, loan_account.debit_account_id, payment_txn.account_txn_ref | 지급·중도상환·청약철회가 연결됨. 아래 설명 참고. pricing_preference.account_id(급여 이체 계좌)는 비어 있음 |
| 카드 (`cards`) | pricing_preference.card_id | 비어 있음 |
| 메인 화면 (`/api/home`) | (테이블 연결 없음) loan_account · repayment_schedule · product_catalog 조회 | `loan/summary.py`가 읽어 `loans` 요약으로 내려줌 |

**계좌 연동** (공통.md 8장, dev/account/backend-spec.md 7.3):

- 실행(본인 지급 대출): 내 저축예금 `accountId`에 `loan_disbursement` 거래로 입금하고 `disbursement.account_txn_ref`에 거래 id를 남긴다. 임대인·매도인·딜러 지급과 대환은 타행 지급이라 우리 계좌에 기록하지 않는다.
- 중도상환: 내 저축예금에서 상환 총액을 `loan_repayment`로 출금한다(잔액이 모자라면 `422 INSUFFICIENT_BALANCE`, 대출 잔액은 그대로).
- 청약철회: 받은 계좌에서 원금+약정 이자(3일)+부대비용을 `loan_repayment`로 되돌려 받는다. 잔액이 모자라면 철회가 거부된다.
- 거래의 `ref_type = 'loan'`, `ref_id = 계약번호`로 어떤 대출의 거래인지 찾는다.
- 대출 쪽 호출은 커밋하지 않는다. 같은 DB 세션이라 대출 실행과 계좌 입출금이 한 트랜잭션으로 묶이고, 하나라도 실패하면 모두 되돌아간다.

## 5. 보안·오류 방지 가드레일

| 구분 | 적용 내용 | 위치 |
|---|---|---|
| SQL 주입 방지 | 모든 쿼리 바인딩 강제(params가 튜플/딕셔너리가 아니면 거부), 여러 문장 실행 거부, insert/update는 **실제 스키마에 있는 테이블만** 허용·식별자 검증, WHERE 없는 전체 갱신 금지 | `database.py` |
| 트랜잭션 | SAVEPOINT 기반 중첩 트랜잭션, 예외 시 전부 롤백 | `database.py` |
| 감사 로그 | 모든 상태 변경·실행·상환을 기록, 직전 행 해시를 이어 붙인 **해시 체인**(위변조 탐지), DB 트리거로 **수정·삭제 차단** | `database.py`, `schema.sql` |
| 상태 머신 | 허용된 단계로만 이동, 약정 전 실행 등 건너뛰기 차단 | `state_machine.py` |
| 동의 게이트 | 필요한 동의가 없으면 외부 조회(신용·공공·마이데이터) 자체를 하지 않고 `inquiry_log`에 BLOCKED 기록 | `consent.py` |
| 속도 제한 | 같은 신청·같은 출처 조회를 분당 횟수로 제한 | `security.py` |
| 입력 검증 | 타입·범위·허용 목록·길이·제어문자·태그 문자(`< > { } \``) 차단, 한도 초과 시 "한도금액을 초과하였습니다." | `validation.py`, `cli.py` |
| 개인정보 보호 | 계좌번호·사번 원문 미저장(마스킹 + HMAC), 로그 출력 전 주민번호·전화·계좌 패턴 자동 마스킹, LLM에 보내기 전 마스킹 | `security.py`, `llm_gateway.py` |
| 이중 실행 방지 | 대출 실행·중도상환에 멱등 키(UNIQUE), 같은 키 재요청은 `DuplicateRequest` | `application.py`, `management.py` |
| 대환 사가 | 견적→실행 보류→상환 송금→완제 확인, 어느 단계든 실패하면 보상(지급 취소·사가 COMPENSATED·신청 REFI_FAILED), 대출 계좌 미개설 | `refinance.py` |
| 파일 검사 | 확장자 허용 목록, 10MB 이하, **파일 앞부분 시그니처가 확장자와 일치**하는지(위장 실행 파일 차단), SHA-256 기록 | `evidence.py` |
| LLM 가드레일 | 기본은 외부 호출 없는 offline 제공자, 출력 검증 V1 스키마·V2 대상 실재·V3 수치 일치·V5 금지 표현·V6 필수 문구(+추천 V4·V7·V8·V9), 하나라도 실패하면 고정 문구로 대체, 호출은 `llm_call_log`에 마스킹 기록. 외부 LLM은 키·계약이 없으면 차단 | `llm_gateway.py`, `recommendation.py` |
| 규제 한도 | DSR 40%(스트레스 +1.0%p), LTV·전세 비율, 최종 금리 법정 최고 20% CHECK, 적합성 상환 부담률 70% | `config.py`, `underwriting.py`, `schema.sql` |

## 8. 한계와 앞으로 할 일

- **외부 연동은 자리만 있음**: 신용평가·공공기관·마이데이터·보증기관·타행 이체는 체험용 데이터로 대신합니다. 실제 연동 시 `consent.gate()`를 통과한 뒤 호출하도록 같은 위치에 연결하면 됩니다.
- **외부 LLM**: 지금은 offline 제공자만 동작합니다. 자체 게이트웨이 API를 만들면 `llm_gateway.py`의 제공자 클래스만 바꾸면 되고, 검증·대체·기록 흐름은 그대로 유지됩니다.
- **신청 진행 상태**: `router.py`의 `Session`을 30분간 메모리에 두고, 요청마다 `loan_application.session_state`(JSONB, 마이그레이션 0003)에도 저장한다. 서버를 다시 켜면 내 신청이 7일 만료 전이고 끝나지 않았을 때 DB에서 복원한다. `shortcut:` 추천 후보는 저장하지 않아 재시작 뒤 `choose` 전에 추천을 다시 조회해야 한다.
- **증빙 파일 업로드**: `POST /api/loans/applications/{id}/docs/upload`(multipart `docKey`·`file`)로 pdf·png·jpg(시그니처로 확인, 10MB, 신청당 20개)를 `backend/data/evidence/`에 저장한다. OCR·LLM 추출은 하지 않는다. `shortcut:` 큰 본문은 앞단(프록시)에서 크기를 제한해야 한다.
- **자동이체 배치**: `loan/batch.py`가 매일 00:20 KST에 납입일이 지난 ACTIVE 대출을 자동이체 계좌에서 출금한다(`loan_repayment` 거래, 같은 날 두 번 돌아도 이중 출금 없음, 밀린 회차는 따라잡음). 잔액이 모자라면 출금하지 않고 납입일을 두어 다음 실행에서 다시 시도한다. `shortcut:` OVERDUE 전환·연체 이자는 만들지 않았다. 개발 모드에서는 `POST /api/dev/loans/auto-debit/run?today=`로 직접 실행한다. 저축예금 해지 때 이 대출의 자동이체 계좌인지 확인한다(`ACCOUNT_LINKED_LOAN`).
- **감사 로그 직렬화**: 해시 체인이 갈라지지 않도록 감사 기록 때 advisory lock을 잡고 트랜잭션이 끝날 때 풀립니다. 요청이 짧아서 문제는 없지만, 대출 쓰기 요청끼리는 순서대로 처리됩니다.
- **날짜·시각·JSON은 문자열로 읽음**: 기존 로직이 ISO 문자열과 `json.loads`를 전제로 해서 `database.py`가 이 컬럼들을 문자열로 읽습니다(`shortcut:` 주석). 로직을 네이티브 타입으로 바꿀 때 걷어냅니다.
- **오류 코드**: 대출 코드는 `common/오류코드.md`에 정리했습니다.
- **화면**: 내 대출 관리 화면(`/loans`: 목록·상품·상세·상환 일정·중도상환·청약철회)은 `frontend/src/features/loans/`에 있다. 신청 단계 화면은 아직 없다. `Prototype/`의 HTML과 `Design/` 시안을 기준으로 `/api/loans`의 신청 API를 호출하면 된다.
