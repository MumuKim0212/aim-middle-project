# 0. 개발 공통 명세 (API · 오류 · 계산 기준 · 목업)

[← 카드 기획서 개요](README.md)

기능별 문서(01~07)의 API 명세가 공통으로 쓰는 규칙을 모은 문서다. 개발자는 이 문서를 먼저 읽고 기능 문서를 본다.

DB 설계, 서버 구현 규칙(동시성·멱등성 저장·서버 간 계약), 프론트 구조·API 클라이언트·목업 제어 같은 **개발 명세**는 기획서가 아니라 [백엔드 개발 명세](../dev/card/backend-spec.md)와 [프론트 개발 명세](../dev/card/frontend-spec.md)에 따로 둔다.

## 1. API 공통 규칙

### 1.1 기본

| 항목 | 규칙 |
|------|------|
| Base URL | `/api/v1` |
| 형식 | JSON (UTF-8), HTTPS |
| 시간대 | 서버 기준 `Asia/Seoul`. "오늘"은 KST 날짜 |
| 인증 | `Authorization: Bearer <accessToken>` 필수. 없거나 만료되면 `401 AUTH_REQUIRED` |
| 소유권 | 로그인 회원 소유가 아닌 리소스는 존재 여부를 숨기려고 `404`로 응답한다 (`403` 쓰지 않음) |

### 1.2 값 형식

| 종류 | 형식 | 예 |
|------|------|-----|
| 금액 | 정수(원). 소수 없음. 부호는 `kind`로 표현하고 금액은 양수 | `1250000` |
| 날짜 | `YYYY-MM-DD` | `2026-11-04` |
| 일시 | ISO 8601, `+09:00` 포함 | `2026-11-04T09:43:18+09:00` |
| ID | 문자열. 내용에 의미를 두지 않는다 | `card_002` |
| enum | 소문자 snake_case 문자열. 단 오류·사유 코드(`code`, `reason`, `blockReason`, `rejectReason` 등)는 대문자 SNAKE_CASE | `active`, `report_lost` / `INCOME_INSUFFICIENT` |
| null | 해당 없는 필드는 **생략하지 않고 `null`** 로 내려준다 | `"paymentDay": null` |
| 카드 번호 | 마스킹 문자열만. 전체 번호·CVC는 어떤 응답에도 없다 | `****-****-****-1234` |
| 계좌 번호 | 마스킹 문자열만 (끝 4자리) | `****1234` |

### 1.3 성공 응답

- 단건 조회·처리 결과: 리소스를 그대로 본문에 담는다 (감싸는 `data` 없음).
- 목록: `{ "items": [ ... ] }`. 결과가 없어도 `200` + 빈 배열.
- 페이지가 있는 목록: `{ "items": [ ... ], "nextCursor": "..." | null }`.
- 새로 만든 리소스: `201`.

### 1.4 오류 응답

```json
{
  "code": "VALIDATION_FAILED",
  "message": "입력값을 확인해 주세요.",
  "details": {
    "fields": [
      { "field": "from", "reason": "FROM_AFTER_TO" }
    ]
  }
}
```

- 프론트는 **`code`로 분기**한다. `message`는 보조 문구이며 화면에는 기능 문서의 문구표를 쓴다.
- `details`의 모양은 오류 코드마다 3절 표에 정해 두었다.

### 1.5 서버 처리 순서

모든 쓰기 API는 아래 순서로 검사하고, **처음 실패한 단계의 오류만** 돌려준다.

1. 인증 (`401`)
2. 요청 형식·입력값 검증 (`400`)
3. 리소스 조회·소유권 (`404`)
4. 상태·업무 조건 (`409`, `422`)
5. 계좌 암호 검증 (`403`, `429`)
6. 실행 (같은 트랜잭션 안에서 상태 변경)

계좌 암호는 **마지막에** 검사한다. 앞 단계에서 걸러질 요청이 암호 오류 횟수를 쓰지 않게 하려는 것이다.

카드 신청([06](06-issuance.md))은 2단계와 3단계 사이에 멱등성 확인(같은 `Idempotency-Key`로 이미 처리했으면 저장된 응답을 돌려주고 끝)이 한 단계 더 들어간다.

### 1.6 페이지 나누기 (커서 방식)

- 요청: `limit`(1~50, 기본 20), `cursor`(이전 응답의 `nextCursor`)
- 응답: `nextCursor`가 `null`이면 마지막 페이지다.
- 커서는 서버만 해석하는 불투명 문자열이다. 조회 조건(필터)이 달라진 요청에 이전 커서를 쓰면 `400 INVALID_CURSOR`.

### 1.7 중복 요청 방지

- `POST /card-applications`는 `Idempotency-Key` 헤더(UUID v4)가 **필수**다. 없으면 `400 IDEMPOTENCY_KEY_REQUIRED`, UUID 형식이 아니면 `400 VALIDATION_FAILED`(`field: "Idempotency-Key"`, `reason: INVALID_FORMAT`)다.
- 키는 **회원별**로 구분한다. 같은 회원이 같은 키로 다시 보내면 처음 응답을 그대로 돌려주고 새로 처리하지 않는다. 키는 24시간 보관한다. 같은 키에 다른 본문(`accountPin`, `cardPin`은 비교에서 뺀다)이 오면 `422 IDEMPOTENCY_KEY_REUSED`.
- 저장하는 응답은 **`201`(승인·거절 모두)뿐**이다. 오류 응답과 `5xx`는 저장하지 않으므로, 같은 키로 다시 시도하면 새로 처리한다.
- 같은 키의 요청이 동시에 둘 오면 하나가 끝난 뒤 나머지가 저장된 응답을 돌려받는다.
- 상태 변경 API(정지·해제·분실·해지)는 키 없이도 안전하다. 이미 바뀐 상태에서 다시 요청하면 `409 CARD_STATE_INVALID`가 되기 때문이다.
- 동시에 같은 카드의 상태를 바꾸는 요청이 들어오면, 상태 조건을 건 갱신(`현재 상태가 허용 상태일 때만 변경`)으로 하나만 성공시키고 나머지는 `409`를 돌려준다.

### 1.8 보안·로그

- `accountPin`, `cardPin`, 인증 토큰은 **로그·오류 응답·분석 도구·화면에 남기지 않는다**. 요청 본문 로깅에서 이 필드들을 제외한다.
- `cardPin`은 형식·단순도(`PIN_TOO_SIMPLE`)만 검증하고 **저장하지 않는다** (이 범위에 카드 비밀번호를 쓰는 기능이 없다). `accountPin`도 저장하지 않고 계좌 도메인의 검증만 호출한다.
- 응답에 카드 전체 번호, CVC, 계좌 전체 번호, 해지 사유(`terminatedReason`)를 담지 않는다.

## 2. 필드 오류 사유 코드

`VALIDATION_FAILED`의 `details.fields[].reason`에 쓰는 값이다.

| reason | 뜻 |
|--------|----|
| `REQUIRED` | 필수 값이 없음 |
| `INVALID_FORMAT` | 형식이 맞지 않음 (날짜, 전화번호, 4자리 숫자 등) |
| `INVALID_ENUM` | 허용되지 않은 값 (알 수 없는 enum, 존재하지 않는 상품 등) |
| `OUT_OF_RANGE` | 숫자 범위를 벗어남 |
| `TOO_LONG` | 길이 초과 |
| `NOT_ALLOWED` | 이 요청에서는 보내면 안 되는 필드 |
| `MUST_BE_TRUE` | 반드시 `true`여야 하는 값 (약관 동의, 유의사항 확인) |
| `PIN_TOO_SIMPLE` | 카드 비밀번호가 너무 단순함 |
| `PRODUCT_TYPE_MISMATCH` | 상품 종류와 카드 종류가 다름 |
| `FROM_AFTER_TO` | 시작일이 종료일보다 늦음 |
| `TO_IN_FUTURE` | 종료일이 오늘 이후 |
| `PERIOD_TOO_LONG` | 조회 기간이 12개월 초과 |

## 4. 계좌 암호 검증

정지·해제·분실 신고·카드 신청·해지는 모두 같은 방식으로 계좌 암호를 확인한다.

### 4.1 요청

- 요청 본문의 `accountPin`: 문자열, 정규식 `^[0-9]{4}$`
- 검증 대상 계좌: 카드 쪽 기능은 **그 카드의 결제 계좌**, 카드 신청은 **신청서에서 고른 결제 계좌**

### 4.2 검증 계약 (계좌 도메인이 제공)

`verifyAccountPin(accountId, pin)`의 결과는 아래 넷 중 하나다.

| 결과 | 카드 API의 응답 |
|------|-----------------|
| 일치 | 다음 단계(실행)로 진행 |
| 불일치 (`remainingAttempts` 1~4) | `403 ACCOUNT_PIN_MISMATCH` + `remainingAttempts` |
| 잠김 (`retryAfterSeconds`) | `429 ACCOUNT_PIN_LOCKED` + `retryAfterSeconds`, `Retry-After` 헤더 |
| 서비스 장애 | `503 ACCOUNT_SERVICE_UNAVAILABLE` (카드 상태는 바꾸지 않음) |

### 4.3 잠금 정책 (확정)

- 오류 횟수는 **계좌 단위**로 센다. 같은 계좌를 결제 계좌로 쓰는 모든 카드, 계좌 도메인의 자체 기능이 같은 카운터를 공유한다.
- **연속 5회** 틀리면 **5분(300초)** 동안 잠근다. 5번째 틀린 요청의 응답부터 `429`(`retryAfterSeconds: 300`)다. (`remainingAttempts: 0`인 `403`은 없다.)
- 잠긴 동안은 올바른 암호를 보내도 `429`이고, 잠금 시간은 늘어나지 않는다.
- 잠금은 5번째 오류 시각부터 300초 동안이다. 정확히 300초가 지난 시점부터 입력할 수 있다. `retryAfterSeconds`는 남은 시간을 올림한 초(잠겨 있는 동안 1 이상)다.
- 잠금이 풀리면 카운터는 0부터 다시 센다. 암호가 맞으면 카운터를 0으로 되돌린다.
- 형식 오류(`400`)와 앞 단계에서 걸린 요청(`404`, `409`)은 횟수에 넣지 않는다.
- 오류 횟수 증가는 요청 처리 트랜잭션이 롤백돼도 **남아 있어야** 한다 (별도 커밋).

### 4.4 화면 규칙 (암호 입력 팝업 공통)

- 입력: 숫자 4자리, `type="password"`, `inputMode="numeric"`, `maxLength=4`, `autoComplete="off"`. 값은 화면에 보여주지 않는다.
- 요청을 보낸 직후(성공이든 실패든) 입력값을 지운다.
- 틀렸을 때: "계좌 암호가 올바르지 않습니다. (남은 시도 N회)"
- 잠겼을 때: "계좌 암호를 5회 연속 틀려 M분 S초 뒤에 다시 입력할 수 있습니다." 입력창과 확인 버튼을 비활성화하고 `retryAfterSeconds`부터 초 단위로 줄여 보여준다. 0이 되면 입력을 다시 연다.
- 정지·해제·분실 신고·카드 신청·해지는 모두 이 팝업으로 암호를 받는다 (폼 안에 인라인 입력창을 두지 않는다). 같은 컴포넌트(`AccountPinDialog`)를 쓴다.

## 5. 카드 상태 전이 (서버 기준)

| 동작 | 허용되는 현재 상태 | 결과 상태 | 그 밖의 상태에서 요청하면 |
|------|--------------------|-----------|---------------------------|
| 신규 발급 | (카드 없음) | `active` | - |
| 일시정지 | `active` | `suspended` | `409 CARD_STATE_INVALID` |
| 정지 해제 | `suspended` | `active` | `409 CARD_STATE_INVALID` |
| 분실 신고 | `active`, `suspended` | `lost` | `409 CARD_STATE_INVALID` |
| 해지 | `active`, `suspended`, `lost` | `terminated` | `409 CARD_STATE_INVALID` |

- `lost`와 `terminated`에서는 `active`·`suspended`로 돌아갈 수 없다.
- 상태가 바뀔 때마다 이력(카드, 이전 상태, 새 상태, 일시, 동작)을 서버에 남긴다. 이력 조회 API는 이번 범위에 없다.
- 카드 상세 응답의 `availableActions`는 아래 표대로 서버가 계산해서 내려준다. 프론트는 버튼 표시를 이 배열로만 정한다.

| 카드 상태 | `availableActions` |
|-----------|--------------------|
| `active` | `view_transactions`, `view_limit`, `suspend`, `report_lost`, `terminate` |
| `suspended` | `view_transactions`, `view_limit`, `resume`, `report_lost`, `terminate` |
| `lost` | `view_transactions`, `view_limit`, `terminate` |
| `terminated` | `view_transactions` |

`terminate`가 있어도 미결제 금액이 있으면 해지 단계에서 막힌다 ([07](07-termination.md)).

## 6. 금액 계산 기준 (공통)

청구액, 이용 금액, 잔여 한도, 해지 가능 판정이 모두 이 규칙 하나를 쓴다. 기능마다 따로 계산하지 않는다.

### 6.1 용어

- **결제일 `D`**: 카드의 `paymentDay`(1~28).
- **청구 주기**: 결제일 날짜 `P` 하나. 이용기간은 `P`가 속한 달의 **전월 1일 ~ 전월 말일**이다.
- **오늘 `T`**: KST 기준 오늘 날짜.

### 6.2 거래가 속하는 결제일

- **일시불 승인**: 거래가 발생한 달의 **다음 달 `D`일**이 결제일이다. (예: 10월 5일 승인, `D=25` → 11월 25일) 이 날짜를 승인의 결제일 `P_a`라고 한다.
- **취소**: 취소 일자 `c`(KST 날짜)와 원 승인의 결제일 `P_a`를 비교한다.
  - `c ≤ P_a` (결제일 당일 포함): 원 승인과 **같은 주기 `P_a`** 에서 차감한다. (예: 10월 30일 승인 → `P_a` 11월 25일, 11월 2일 취소 → 11월 25일 청구에서 차감)
  - `c > P_a`: 이미 결제된 건의 취소다. **취소가 일어난 달의 다음 달 `D`일** 청구에서 차감한다. (예: 9월 12일 승인 → `P_a` 10월 25일, 11월 2일 취소 → 12월 25일 청구에서 차감)
- **할부 승인** (금액 `A`, 개월 수 `n`, 발생월 `m`): 회차 `i`(1~n)의 결제일은 `m + i`월 `D`일이다. 회차 1은 일시불과 같은 결제일이다.
  - 회차 금액: `i < n`이면 `floor(A / n)`, 마지막 회차는 `A − floor(A / n) × (n − 1)`.
  - 예: 1,000,000원 3개월 → 333,333 / 333,333 / 333,334

### 6.3 청구액 `B(P)` (카드별)

```
B(P) = Σ 일시불 승인(결제일 = P) − Σ 취소(결제일 = P) + Σ 할부 회차(결제일 = P)
```

- 결과가 음수면 `0`으로 본다. 남는 차감분(이미 결제된 건의 환급분이 그 주기 청구액보다 큰 경우)은 다음 주기로 넘기지 않고 없어진다 (단순화).

### 6.4 결제 상태

- `P < T` 이면 **결제 완료**, `P ≥ T` 이면 **미결제**다. 결제일 **당일은 미결제**로 본다.

### 6.5 이용 금액·잔여 한도 (신용카드)

```
이용 금액(used)  = Σ B(P)   (P ≥ T 인 모든 주기)
잔여 한도        = max(0, 총 한도 − used)
이용 비율        = min(100, round(used ÷ 총 한도 × 100, 소수 첫째 자리))
```

### 6.6 다음 결제일

- 카드별 **다음 결제일** = `T` 이후(당일 포함) 가장 가까운 `D`일. 이번 달 `D`일이 `T` 이상이면 이번 달, 아니면 다음 달이다. (청구 화면의 `nextPaymentDate`는 청구액이 있는 묶음 중 가장 빠른 결제일이라 이 값과 다를 수 있다.)

### 6.7 해지 가능 (신용카드)

- `used == 0` 이면 해지할 수 있다.
- 해지 불가 안내의 `unpaidAmount` = `used`, `firstDueDate` = `B(P) > 0`인 주기 중 가장 빠른 `P` (미결제 청구가 처음 결제되는 날). 6.6의 다음 결제일과는 다른 값이다.

### 6.8 데이터 규칙

- **취소는 일시불 승인에만 생긴다** (할부 취소는 다루지 않는다). 승인 한 건에 취소는 최대 1건이고 금액은 원 승인과 같다. 취소 일시는 원 승인 일시보다 뒤다.
- 체크카드 거래는 청구·이용 금액에 포함하지 않는다.
- 일시정지·분실 카드도 같은 규칙으로 계산한다.

## 9. 화면 공통 처리

모든 카드 화면이 같은 방식으로 처리하는 상황이다. 기능 문서에 그 화면만의 문구가 있으면 그것을 쓰고, 없을 때만 이 표의 문구(기본 문구)를 쓴다.

| 상황 | 처리 |
|------|------|
| `401 AUTH_REQUIRED` | 로그인 화면으로 이동. 로그인 후 원래 화면으로 돌아온다 |
| `500`, `503`, 네트워크 오류, 10초 타임아웃 | (기본 문구) "일시적인 오류가 발생했습니다. 잠시 후 다시 시도해 주세요" + 다시 시도 버튼 |
| 로딩 | 영역별 로딩 표시 (화면 전체를 막지 않는다) |

- 금액·날짜 표기(`1,234,000원`, `2026.11.04`)는 모든 화면이 같은 방식으로 한다.
- 쓰기 요청(정지·해제·분실·신청·해지)이 성공하면 카드 목록·상세를 다시 조회해 새 상태를 보여준다.
- 프론트 폴더 구조, API 클라이언트, 목업 서버 제어, 암호 팝업 컴포넌트 같은 구현 사항은 [프론트 개발 명세](../dev/card/frontend-spec.md)에, DB 설계·동시성·서버 간 계약은 [백엔드 개발 명세](../dev/card/backend-spec.md)에 있다.
