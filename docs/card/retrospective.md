## 2. 잘한 점 (Keep)

- **문서를 먼저 확정했다.** 기능별 문서에 API 명세·검증·오류 처리·테스트 시나리오를 함께 넣어, 구현이 문서를 따라가면 되는 구조였다. 시나리오 52개가 그대로 문서의 테스트 절에서 나왔다.
- **돈과 직결된 부분의 경합을 설계에서 다뤘다.** 카드 신청은 `Idempotency-Key` + `card_issue_quota` 행 잠금으로 중복 신청과 3장 제한 초과를 막고, 암호 오류 횟수는 요청 트랜잭션과 별도로 커밋해 롤백돼도 카운트가 남는다.
- **범위 밖을 명시했다.** 재발급·한도 변경·실제 결제 승인을 기획서에서 제외해 범위가 늘어나지 않았다.
- **카드 안에서 구조를 닫았다.** 모든 코드가 `features/card/`와 `cards.py`에 모여 다른 담당자의 영역(계좌·대출·가계부)을 건드리지 않았다.

## 3. 아쉬운 점 (Problem)

- **계획과 구현이 어긋났다.** 기획서는 "프론트 먼저, `features/card/mock/`의 목업으로 시작"이었는데 실제로는 목업 없이 실제 백엔드에 붙였다. 프론트 명세의 6장(목업 서버)은 구현되지 않았고, 문서가 현재 코드와 다르다.
- **의존 기능이 없어 임시값을 넣었다.** 로그인이 없어 `current_member()`가 데모 회원을 고정으로 돌려주고, 계좌 암호는 데모 값(`1234`)으로 검증한다. 카드 → 계좌 서버 간 계약(백엔드 명세 5장)은 실제로 검증하지 못했다.
- **한 커밋에 7,000줄이 들어갔다.** `a07d1e4` 하나가 45개 파일, +7,220줄이다. 백엔드·프론트·테스트·문서를 나눠 커밋했다면 리뷰와 되돌리기가 쉬웠을 것이다.
- **합의 항목이 남아 있다.** 회원(`members`) 테이블 소유자, 일반 계좌 테이블(김연준)이 아직 "제안안"이다. 카드 쪽 계좌 테이블은 카드 명세에서 역산한 값이다.

## 4. 다음에 시도할 것 (Try)

- 문서와 구현이 갈라지는 순간 문서를 같이 고친다 (특히 프론트 명세 6장 목업 서버: 삭제하거나 "미구현"으로 표시).
- 기능 단위(백엔드 / 프론트 / 테스트)로 커밋을 나눈다.
- 계좌·회원 담당과 인터페이스(백엔드 명세 5장)를 먼저 맞추고, 데모 암호·고정 회원을 걷어낼 시점을 정한다.
- 시나리오 52개는 PostgreSQL이 있어야 돌아가므로 CI에서 실행되게 만든다.

## 5. 아직 확인하지 못한 것

- 이번 회고를 쓰면서 테스트를 다시 실행하지 않았다. 통과 여부는 커밋 메시지의 기록을 따랐다.
- 화면 10개의 실제 동작과 모바일 레이아웃은 이 문서 작성 시점에 눈으로 확인하지 않았다.
