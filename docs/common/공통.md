## 0. 이 문서의 쓰임

- 파트마다 같은 내용을 따로 적다가 어긋나지 않도록, **여러 파트가 함께 지키는 규칙을 이 문서 한 곳에만** 적는다.
- 파트 문서(회원-인증.md, 계좌.md, card/*, 가계부, 대출)는 이 문서의 규칙을 **복사하지 않고 링크한다.** 파트 문서가 이 문서와 다르면 파트 문서를 고친다.
- 규칙 뒤의 `(출처: …)`는 처음 정한 문서다. 출처 문서 쪽 내용이 바뀌면 이 문서를 같이 고친다.
- 기능별 규칙(이자 계산, 청구 계산, 가입 항목 등)은 넣지 않는다. 각 파트 문서가 소유한다.
- **소유와 변경 절차**: 이 문서와 `common/` 아래 문서의 기준본은 `main` 브랜치다. 누구나 고칠 수 있지만 **`main`에서만** 고친다. 파트 브랜치(feature/*)에서 이 문서를 고치지 않는다. 파트 브랜치에서 규칙을 바꿔야 하면 먼저 `main`에서 이 문서를 고치고 파트 브랜치가 그 내용을 가져온다. 규칙을 바꿀 때는 결정기록.md 12장 변경 이력에 적고, 영향받는 파트 문서와 결정기록.md 11장 반영 현황을 같은 날 고친다.

## 1. 기술 구조

- 스택: FastAPI + React(Vite) + PostgreSQL/pgvector + Gemini API (출처: 회원-인증.md 11장, 2026-11-05 결정). 기술 선택의 상세(버전, Gemini 모델, 폴더 구조, 개발 환경 세팅)는 [기술스택.md](기술스택.md)가 기준이고, 이 절은 파트가 함께 지킬 구조 규칙만 적는다.
- 백엔드는 **한 서버(모놀리스)** 이고 파트는 모듈이다. 파트 사이 호출은 HTTP가 아니라 같은 프로세스의 함수 호출이다.
- 모든 API는 `/api` 아래에 둔다. 버전 접두(`/api/v1`)는 쓰지 않는다. 개발 중에는 Vite proxy로 `/api`를 백엔드에 넘겨 같은 출처로 동작시킨다.
- 로그인 상태는 서버 세션 쿠키(Starlette SessionMiddleware, 서명된 쿠키)로 유지한다. JWT와 `Authorization` 헤더는 쓰지 않는다. (출처: 회원-인증.md 5.3)
- 스키마는 Alembic 마이그레이션으로 관리한다 (`backend/alembic/`, 2026-11-06 전환). 서버는 시작할 때 테이블을 만들지 않고, DB 가 최신 마이그레이션이 아니면 `alembic upgrade head`를 안내하며 멈춘다. 시드는 서버가 시작할 때 넣는다. 모델이나 대출 `schema.sql`을 고치면 마이그레이션을 새로 쓴다(`tests/test_migrations.py`가 어긋나면 알려 준다). 기술스택.md 9장에 사용법이 있다.

## 3. 인증·접근 제어 (API 규약)

회원-인증.md 6장(R1~R10)이 원본이다. 파트가 구현할 때 필요한 것만 요약한다.

| 규칙 | 내용 |
|---|---|
| 보호 장치 | 로그인 필요 API는 모두 `user: User = Depends(current_user)`를 쓴다. `user_id`는 요청 본문·쿼리에서 받지 않고 세션 값만 쓴다 (R3, R5) |
| 응답 | 미로그인 `401 LOGIN_REQUIRED`, 세션 만료 `401 SESSION_EXPIRED`, 간편비밀번호 미설정 `403 PIN_SETUP_REQUIRED` (R10) |
| 타인 데이터 | 타인의 계좌·카드·거래를 지정하면 존재하지 않는 것과 똑같이 **404**로 응답한다. 403을 쓰지 않는다 (R4) |
| 쓰기 요청 | 상태를 바꾸는 요청은 POST(필요하면 PUT/DELETE)만 받고, GET은 조회만 한다 (R7) |
| CSRF | 세션 쿠키는 HttpOnly, SameSite=Lax. 쓰기 요청에 `Origin` 헤더가 있으면 우리 출처와 같아야 하고, 다르면 403으로 거부한다. `Origin`이 없는 요청(브라우저 밖 클라이언트, 테스트)은 통과시킨다. 폼 토큰 방식은 FastAPI에 기본 지원이 없어 쓰지 않는다 (R7의 "프레임워크 지원 범위 내에서"에 해당) |
| 프론트 처리 | 공통 fetch 래퍼가 `credentials: "include"`를 붙이고, 401이면 `/login?next=<원래 경로>`, 403 `PIN_SETUP_REQUIRED`면 S-07로 보낸다. 서버는 리다이렉트하지 않는다 |
| 세션 | 마지막 활동 후 30분 만료(슬라이딩). 로그인 시 세션 재생성 (5.3) |
| 사용자 정보 | 이름·생년월일은 세션에 담지 않고 요청마다 DB에서 읽는다 (R6). 나이는 `get_age(user)`로 얻는다 |

## 4. 본인 재확인 (2차 인증, 간편비밀번호)

돈이 움직이거나 되돌리기 어려운 동작은 실행 직전에 **간편비밀번호 6자리**를 다시 확인한다. 로그인에 쓰는 6자리와 같은 값이다. (출처: 회원-인증.md R9, S-08)

**적용 동작**

| 파트 | 동작 |
|---|---|
| 계좌 | 이체, 예적금 해지 (계좌.md 5.4, 5.5) |
| 카드 | 일시정지, 정지 해제, 분실 신고, 카드 신청, 카드 해지 |
| 대출 | 대출 실행(계좌 입금), 중도상환, 청약철회 ([loan/README.md](../loan/README.md)). 실행·중도상환은 `Idempotency-Key`도 받는다 |

계좌 암호(4자리)는 쓰지 않는다. 카드 신청의 카드 비밀번호(`cardPin`, 4자리)는 카드를 쓰기 위한 별개의 값이다.

**흐름**

1. 프론트가 동작 직전에 S-08(간편비밀번호 확인)을 띄운다. 이미 5분 안에 확인했으면 띄우지 않는다.
2. S-08이 `POST /api/auth/pin/verify` `{ "pin": "135792" }`를 호출한다. 통과하면 `200 { "verified": true, "validForSeconds": 300 }`이다.
3. 통과하면 서버가 세션에 `pin_verified_at`을 기록한다. 이후 **5분 동안**은 본인 재확인이 필요한 동작을 여러 번 해도 다시 묻지 않는다. 5분이 지나면 다시 확인한다.
4. 업무 API(이체, 카드 정지 등)는 실행 직전에 `pin_verified(request)`로 확인한다. 안 되어 있거나 5분이 지났으면 `403 PIN_VERIFICATION_REQUIRED`로 응답하고, 프론트가 S-08을 다시 띄운다.
5. 업무 API 요청 본문에는 간편비밀번호를 넣지 않는다.

**응답 코드** (`POST /api/auth/pin/verify`)

| HTTP | code | 뜻 | details |
|:---:|---|---|---|
| 200 | - | 통과 | 본문 `{ verified: true, validForSeconds: 300 }` |
| 400 | `VALIDATION_FAILED` | 6자리 숫자가 아님 | `fields` |
| 403 | `PIN_MISMATCH` | 틀림 (로그인 전 `/pin/login`은 401) | `remainingAttempts` (1~4) |
| 403 | `PIN_SETUP_REQUIRED` | 간편비밀번호를 아직 설정하지 않음 | - |
| 423 | `PIN_LOCKED` | 5회 연속 틀려 잠김. 시간이 지나도 풀리지 않고 아이디·비밀번호로 다시 로그인해 재설정해야 풀린다 | - |

**S-08을 부르는 두 가지 방법** (둘 다 구현됨)

- 화면: `/auth/pin/verify?next=<내부 경로>&desc=<동작 설명>`. 통과하면 `next`로 돌아가고(replace), 취소하면 이전 화면으로 간다. 단순한 동작에 쓴다.
- 컴포넌트: `frontend/src/auth/PinKeypad.tsx`(6자리를 다 누르면 자동 제출). 다단계 입력처럼 화면을 벗어나면 입력 상태를 잃는 흐름(카드 신청 등)은 자기 화면 안의 팝업에서 이 컴포넌트로 입력을 받고 `POST /api/auth/pin/verify`를 직접 호출한다.

**횟수·잠금**

- 틀린 횟수(`users.pin_failed_count`)는 **사용자 단위**로 센다. 간편 로그인과 모든 2차 인증이 같은 카운터를 쓴다 (R9).
- 5번째로 틀린 요청의 응답부터 `423 PIN_LOCKED`다. `remainingAttempts: 0`인 403은 없다.
- 맞으면 카운터를 0으로 되돌린다.
- 형식 오류(400)는 횟수에 넣지 않는다.

**보안**

- 간편비밀번호 값은 로그, 오류 응답, chat_messages, 분석 도구, 화면에 남기지 않는다.
- 자연어(채팅)에서는 간편비밀번호를 입력받지 않는다. 확인이 필요하면 프론트가 S-08을 띄운다 (9장).

## 5. 오류 응답 형식

```json
{ "code": "VALIDATION_FAILED", "message": "입력값을 확인해 주세요.", "details": { "fields": [ { "field": "from", "reason": "FROM_AFTER_TO" } ] } }
```

- 형식은 `{ code, message, details? }`다. `details`는 코드마다 모양이 정해져 있을 때만 쓴다. 회원-인증.md 6.1의 `{ code, message }`를 포함하는 형태다.
- 프론트는 **`code`로 분기**한다. `message`는 보조 문구다.
- **전체 코드와 필드 오류 사유(reason)는 [오류코드.md](오류코드.md)가 원본이다.** 파트 문서는 코드 이름만 쓰고 표를 새로 만들지 않는다.
- **코드 표기**: 모든 `code`는 대문자 SNAKE_CASE다 (`LOGIN_REQUIRED`, `PIN_LOCKED`, `VALIDATION_FAILED`, `CARD_NOT_FOUND`). 파트마다 표기를 달리하지 않는다. 필드의 값(enum)은 소문자 snake_case다 (`active`, `report_lost`).
- 공통으로 쓰는 코드(`VALIDATION_FAILED`, `LOGIN_REQUIRED`, `SESSION_EXPIRED`, `PIN_SETUP_REQUIRED`, `PIN_VERIFICATION_REQUIRED`, `NOT_FOUND`, `INTERNAL_ERROR` 등)의 HTTP 상태와 뜻은 [오류코드.md 2장](오류코드.md#2-공통-코드)에 있다. `NOT_FOUND`는 파트가 더 구체적인 코드(`CARD_NOT_FOUND`)를 정했으면 그것을 쓴다.

## 6. 데이터 규칙

| 항목 | 규칙 |
|---|---|
| 금액 | 정수(원), DB `BIGINT`. 소수 없음. 응답의 금액은 양수이고 입금·출금 같은 방향은 `kind`/`type` 필드로 표현한다 |
| 금리 | `NUMERIC(5,2)` (%) |
| 시각 | DB `TIMESTAMPTZ`(UTC 저장). API는 ISO 8601에 `+09:00`을 붙여 내려준다. 화면은 KST |
| 날짜 | `YYYY-MM-DD`. "오늘"은 KST 날짜 |
| JSON 필드 | camelCase. 해당 없는 값은 생략하지 않고 `null`로 내려준다 (card/00에서 승격, 결정기록.md 10장 제안) |
| 회원·계좌 ID | DB `BIGINT IDENTITY`, JSON은 숫자 (`accountId: 1`). **시드로 id를 고정하는 테이블(users, products, accounts)은 `GENERATED BY DEFAULT AS IDENTITY`** 로 만들고 시드 뒤에 시퀀스를 맞춘다 (구현된 users가 이 방식) |
| 파트 자체 ID | 그 파트가 정한다. 카드는 문자열(`card_002`, `tx_201`)을 쓴다 |
| 외래키 | 다른 파트 테이블을 참조할 때는 `BIGINT` 값을 그대로 쓴다. 파트 소유 테이블은 `ON DELETE` 규칙을 두지 않는다 (회원 탈퇴 미구현) |
| 계좌번호 | 저장은 `1002-XXX-XXXXXX` 평문(계좌.md 7.2). **다른 파트의 응답에는 마스킹(`****1234`, 끝 4자리)만** 담는다. 전체 번호는 본인의 계좌 상세 화면에서만 내려준다 |
| 은행명 | 우리 은행 한 곳이라 계좌 테이블에 컬럼을 두지 않는다. 계좌 API가 상수 `"AIM Bank"`를 `bankName`으로 내려준다 |
| 테이블 이름 | 회원은 `users` (dev/auth/backend-spec.md 8.1). 파트 문서가 쓰던 `members`는 `users`로 읽는다. 대화 기록 테이블은 `chat_sessions`(회원별 세션)·`chat_messages`(메시지)다 (구현 기준, 예전 문서의 `chat_messages`는 이 두 테이블로 대체) |

## 9. 자연어 연동 공통

### 9.1 구조

```
홈 입력창 → 라우터 → 도메인 에이전트(auth / acc / card / ledger / loan) → 응답
```

- **라우터**: 사용자의 문장과 최근 대화 맥락을 보고 어느 도메인의 일인지 고른다. 고르지 못하면 되묻는다. 기능을 직접 실행하지 않는다.
- **도메인 에이전트**: 그 파트의 기능 함수(도구)만 호출한다. 한 도메인 에이전트가 다른 도메인 기능을 호출하지 않는다.
- 도구는 Gemini 함수 호출로 구현하고, 파트가 서비스 함수를 제공하면 자연어 담당이 도구로 등록한다 (계좌.md 8장).
- 의도 이름은 `<도메인>.<동작>` 형식이다 (`auth.logout`, `acc.transfer`, `card.suspend`). 도메인 접두가 라우터의 분기 기준이다.
- 라우터와 에이전트의 구현은 자연어 담당 몫이고, 이 문서는 파트가 지킬 계약만 정한다.

### 9.2 모든 에이전트가 지키는 규칙

| 규칙 | 내용 |
|---|---|
| 인증 우선 | 의도를 분류하기 전에 세션의 user를 먼저 확인한다. 미인증이면 허용 의도(가입·로그인 안내, 잠금 안내, FAQ)만 분류하고 나머지는 로그인 링크로 응답한다 (회원-인증.md 9.2) |
| user 주입 | 도구의 `user`는 서버가 세션에서 넣는다. 모델이 정하지 못한다. 문장에 타인의 이름·계좌·카드가 들어 있어도 본인 데이터 범위 안에서만 동작한다 (R8) |
| 비밀값 | 비밀번호, 간편비밀번호, 카드 비밀번호는 채팅으로 받지 않는다. 화면으로 보낸다 (회원-인증.md 9.1) |
| 확인 질문 | 돈이 움직이거나 상태를 바꾸는 동작은 실행 전에 "…할까요?" 확인을 받는다. 도구는 1차 호출에서 `{ status: "confirm_required", summary }`를 돌려주고, 사용자가 "응"이라 한 뒤 2차 호출에서 실행한다 (계좌.md 8장) |
| 본인 재확인 | 2차 호출이 4장의 적용 동작이고 `pin_verified`가 아니면 도구는 실행하지 않고 `{ status: "pin_verification_required" }`를 돌려준다. 프론트가 S-08을 띄우고, 통과하면 같은 실행을 다시 요청한다 |
| 화면 링크 | 다단계 입력이 필요한 동작(개설, 신청, 해지)은 실행하지 않고 해당 화면 링크만 준다 |
| 대상 지정 | 대상이 여러 개면(카드 여러 장, 계좌 여러 개) 별명·종류·끝 4자리로 고르고, 정해지지 않으면 되묻는다 |
| 응답 모양 | `{ text, links: [{ label, path }], action? }`. `action`은 `pin_verification_required` 같은 프론트 동작 지시다 |
| 맥락 | 세션에 최근 5턴, 전체는 chat_messages. 로그아웃·만료 시 세션 맥락은 사라진다 |

### 9.3 채팅 API

홈 입력창이 부르는 API다. 라우터와 에이전트의 내부 구현은 자연어 담당이 정하고, 프론트와 맞물리는 부분만 정한다.

| 항목 | 규칙 |
|---|---|
| 요청 | `POST /api/chat` `{ "message": "..." }`. `Accept: text/event-stream`이면 SSE로 나눠 보낸다(선택). 사용자는 세션에서 얻고 본문에 넣지 않는다 |
| 응답 | `200 { domain, text, links: [{ label, path }], action? }`. `domain`은 `auth`, `acc`, `card`, `ledger`, `loan`, `faq`, `unknown` 중 하나 |
| 로그인하지 않음·만료 | 이 API만 **401을 돌려주지 않는다.** `200`으로 로그인 안내 `text`와 `/login` 링크를 준다 (회원-인증.md 9.2). 허용 의도(가입·로그인 안내, 잠금 안내, FAQ)는 그대로 답한다 |
| 본인 재확인 | `action: { "type": "pin_verification_required" }`를 주면 프론트가 S-08을 띄우고 통과 후 `POST /api/chat/resume`을 호출한다. 서버가 세션의 대기 동작을 실행하고 같은 응답 모양으로 답한다 (9.2, card/08 4절) |
| 실패 | LLM 호출이 실패하면 `503 CHAT_UNAVAILABLE` |
| 기록 | 대화는 `chat_sessions`·`chat_messages`에 남기고 세션에는 최근 5턴만 둔다. 비밀값은 어느 곳에도 남기지 않는다 |
| 기존 가계부 대화 | `/api/ledger/...`의 가계부 전용 대화(구현됨)는 가계부 화면 안의 대화이고 이 API와 별개다. 홈 입력창에서 가계부 의도가 나오면 라우터가 `ledger` 에이전트로 넘긴다 |
