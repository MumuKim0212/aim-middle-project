# 오늘 써도 될까? — 은행 가계부 기획안

## 1. 한 줄 소개

카드 사용 내역으로 월 예산과 카드대금 반영 후 잔액을 계산하고, 결제 전에 “지금 써도 되는지” 알려주는 가계부. 같은 판단 결과를 사용자가 고른 네 가지 말투와 화면으로 보여준다.

> 디자인은 우리은행 모바일 웹의 공통 헤더와 파란색 계열을 참고한 비공식 프로젝트 시안이다. 화면의 계좌와 거래는 모두 예시 데이터다.

## 2. 핵심 화면과 기능

| 화면 | 사용자 행동 | 현재 HTML 데모 | 팀 통합 시 구현 |
|---|---|---|---|
| 요약 | 계좌 잔액, 예정 카드대금 반영 후 예상 잔액, 예산·카테고리 지출 확인 | 예시 데이터로 계산 | 인증 사용자 계좌·카드 거래 API 연결 |
| 결제 전 확인 | 금액과 카테고리 입력, 초과 여부 확인 | 모의 판정과 보류 메시지 | 프로젝트의 모의 카드 승인 흐름에 연결 |
| 소비 내역 | 월 선택, 지출 추가·삭제, 전월 비교 | 브라우저 저장 | 카드 거래 원장 조회, 분류 변경·환불 처리 |
| 예산 설정 | 월·배달 예산, 잔액·예상 잔액 수정 | 브라우저 저장 | 사용자별 예산·예정 지출 저장 |
| 물어보기 | 자연어로 잔액·예산·지난달 지출·결제 가능 여부 질문 | 규칙 기반 금액·항목 인식 | 팀의 자연어 라우터와 대화 상태 연결 |
| 상품·이용 안내 | 은행 상품·혜택·이용 방법 질문 | 미구현 | 팀 RAG 검색 결과와 출처 연결 |

### 네 가지 모드

| 모드 | 화면 | 답변 방식 |
|---|---|---|
| 싸가지 | 불타는 지옥문, 경고 티켓, 어두운 색 | 반말과 직설적 경고. 욕설 강도는 제품 정책과 사용자 설정으로 조절 |
| 기본 | 푸른 유리 토큰, 은행형 카드 | 차분한 존댓말과 계산 결과 |
| 착한 | 우비 입은 저금통 캐릭터, 부드러운 색 | 반말로 격려하고 절약 시 구체적으로 칭찬 |
| 숫자만 | 표·격자 중심의 정보 화면 | 감정 표현 없이 금액, 비교, 판정만 표시 |

모드는 **표현만** 바꾼다. 같은 거래와 예산이라면 결제 가능·보류 판정은 어느 모드에서나 같다. 사용자는 언제든 모드를 변경할 수 있고, 선택은 저장한다.

## 3. 주요 이용 흐름

1. 로그인한 사용자가 가계부에 들어오면 이번 달 카드 지출, 남은 월 예산, 대표계좌 잔액, 예정 카드대금 반영 후 예상 잔액을 본다.
2. “오늘 배달 2만 원 시켜도 돼?”라고 입력한다. 카테고리와 금액을 추출하고, 정보가 빠지면 금액·카테고리를 다시 묻는다.
3. 월 예산·카테고리 예산·예상 잔액을 결제 예상액과 비교한다. 어느 하나라도 부족하면 모의 결제를 보류하고 사유와 초과액을 보여준다.
4. 사용자는 금액을 줄이거나 예산을 다시 정한다. 성공한 모의 승인만 지출 원장에 반영한다.
5. 다음 달에는 지난달·지지난달과 지출을 비교하고, 절약한 항목과 증가한 항목을 거래 근거와 함께 본다.

### 계산 원칙

```text
이번 달 순지출 = 승인된 카드 거래 합계 − 해당 거래의 환불 합계
남은 월 예산 = 월 예산 − 이번 달 순지출
카테고리 잔여 = 카테고리 예산 − 해당 카테고리 순지출
결제 후 예상 잔액 = 현재 계좌 잔액 − 예정 출금 − 미결제 카드대금 − 새 결제 시도액
보류 = 결제 시도액이 월 예산 잔여, 해당 카테고리 잔여, 결제 후 예상 잔액 중 하나라도 초과
```

계좌 잔액과 남은 예산은 다른 값이다. 카드 승인 시점에는 예산 사용액과 미결제 카드대금이 늘고, 계좌 잔액은 카드대금이 실제 출금될 때 줄어든다. 현재 HTML은 단순 예시 계산이며 실제 청구 일정은 연결하지 않는다.

## 4. 데이터 구조 초안

| 테이블 | 핵심 필드 | 설명 |
|---|---|---|
| `users` | `id`, `email`, `password_hash` | 팀 공통 인증 사용 |
| `accounts` | `id`, `user_id`, `balance`, `masked_number` | 본인 계좌만 조회 |
| `card_transactions` | `id`, `user_id`, `card_id`, `amount`, `merchant`, `category`, `approved_at`, `status`, `refund_of` | 승인·거절·환불 구분 |
| `budgets` | `id`, `user_id`, `month`, `total_amount`, `emergency_floor` | 월별 전체 예산과 최소 잔액 |
| `category_budgets` | `budget_id`, `category`, `amount` | 카테고리별 한도 |
| `planned_outflows` | `id`, `user_id`, `due_date`, `amount`, `type` | 카드대금·고정비 등 예정 출금 |
| `payment_attempts` | `id`, `user_id`, `amount`, `category`, `result`, `reason`, `created_at` | 모의 결제 보류 근거 기록 |
| `chat_sessions`, `chat_messages` | `user_id`, `role`, `content`, `intent`, `context_json` | 후속 질문 맥락 |
| `rag_documents` | `id`, `source_url`, `title`, `version`, `chunk_text` | 상품·이용 안내 검색용 문서 |

금액은 정수 원 단위로 저장하고 서버에서 다시 계산한다. 사용자의 `user_id`는 요청 본문을 믿지 않고 인증 세션에서 결정한다. 카드 거래와 결제 시도 기록은 분리한다.

## 5. 자연어와 RAG 연결

- **정형 데이터 질문:** 잔액, 지난달 지출, 예산, 결제 가능 여부는 인증된 사용자의 DB를 조회하고 계산 함수로 답한다.
- **문서 질문:** 상품 금리·가입 조건·카드 혜택·서비스 안내는 승인된 문서를 RAG로 검색해 출처와 기준일을 함께 답한다.
- **혼합 질문:** “돈 남으면 어떤 적금이 좋아?”는 먼저 가계부의 실제 여유액을 계산하고, 상품 추천 근거는 RAG에서 가져온다.
- **후속 질문:** “그럼 1만 원은?”처럼 금액만 바뀌면 직전 카테고리를 유지한다. 사용자별 대화 상태는 분리한다.
- **불확실성:** 금액·날짜·카테고리가 모호하면 실행 전에 재질문한다. 문서에 근거가 없으면 추측하지 않는다.

## 6. 알림·보상과 실패 상황

월 예산 70%에서는 주의, 90%에서는 강한 경고, 초과 시 모의 결제 보류를 기본값으로 검토한다. 카테고리 예산도 별도로 평가한다. 긍정 알림은 “얼마를 덜 썼는지”와 근거 기간을 함께 보여준다. 실제 여행 예약이나 쿠폰 지급은 이 범위에 넣지 않는다.

| 상황 | 기대 동작 |
|---|---|
| 월 예산이나 배달 예산 초과 | 모의 결제 보류, 초과 기준과 금액 표시, 거래 미반영 |
| 예정 카드대금 반영 후 잔액 부족 | 결제 전 경고·보류 |
| 요청 금액 누락 | 금액을 다시 질문, 임의 승인 금지 |
| 환불 발생 | 원거래와 연결하고 순지출 재계산 |
| 로그인하지 않음 | 개인 계좌·카드 내역을 보여주지 않고 로그인으로 안내 |
| RAG 근거 없음 | 출처 없는 상품 조건을 만들지 않고 확인 불가 안내 |

## 7. 구현 순서

1. 팀 공통 인증·계좌·카드 거래 모델 확인
2. 월간 집계와 예산·예상 잔액 계산 함수 구현
3. 가계부 요약·거래 내역·예산 설정 API와 모바일 화면 연결
4. 모의 카드 승인 전 예산 판정 연결, 실패 상황 테스트
5. 자연어 의도 라우팅과 대화 상태 연결
6. 상품·혜택 안내 RAG 연결 및 출처 검증
7. 네 가지 모드와 알림·칭찬 문구 다듬기

## 8. 현재 프로토타입 확인 결과와 한계

현재 HTML에서 모드 변경, 예시 카드 지출 추가·삭제, 월별 조회, 예산 수정, 결제 보류, 규칙 기반 질문, 브라우저 저장을 확인했다. 10,000원 지출 추가 후 월 지출이 612,000원에서 622,000원, 남은 예산이 188,000원에서 178,000원으로 변경됐고 새 탭에서도 유지됐다. 20,000원 배달 시도는 카테고리 잔여 9,000원을 초과하여 보류됐다. 테스트 기록은 초기화했다.

HTML은 금융기관 연동, 실제 승인, 서버 인증, DB, 생성형 AI, RAG, 알림 전송을 구현하지 않는다. 팀 통합 시 서버 측 재계산과 인증 검사가 필요하다.
