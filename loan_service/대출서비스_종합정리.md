# 대출 서비스 종합 정리

> 기획서(Proposal)와 프로토타입 구현명세의 규칙을 **실행 가능한 파이썬 코드 + DB**로 옮긴 결과물입니다.
> 모든 금리·한도·기준값은 **예시값**이며 실제 상품 조건이 아닙니다.
> 회원·로그인·은행·카드·메인 화면은 아직 만들지 않았으므로, DB에는 **연결할 빈 칸**만 두었습니다. 나중에 합칠 때 그 칸에 FK(또는 API)만 연결하면 됩니다.

## 3. 업무 흐름 (코드 기준)

```
상품 선택 ─ (정부) G01 자격 사전확인
   │
   ▼
C02 약관·동의 ──(필수 미동의)──▶ 중단
   │                       (대환) R03 기존 대출 조회 → R04 대환 자격 → 대상 선택
   ▼
C03 고객정보·적합성 ──(부적합)──▶ 조정 안내 → 고객 확인 시에만 진행
   │   (정부) 소득·자산 요건 / (기관A) 보증기관 선택 / (기관B) 협약기관·재직 확인
   ▼
C04 증빙 제출 (파일 검사·자동연동) → C05 7단계 심사(결격→소득→신용→DSR→담보→한도→판정)
   │                                   └ 거절 / 서류 보완 / 승인 / 조건부 승인
   ▼
C06 권장 상품 3안 (고객 비용 기준 순위 + LLM 사유 + V1~V9 검증)   (대환) R09 유불리 비교
   ▼
C07 조건 확정 → C08 금리 산정(우대) → C09 설명서·이해 확인 퀴즈 → C10 약정(전자서명 자리)
   ▼
C11 담보·보증 설정 → C12 실행(멱등 키) / (대환) 사가: 견적→실행 보류→상환 송금→완제 확인, 실패 시 보상
   ▼
C13 완료 → 대출 계좌 개설 → 대출관리(M01 스케줄, M05 중도상환, M06 금리인하, M07 철회, 기간연장, 증명서)
```

신청서 상태는 `loan/state_machine.py`의 허용 목록으로만 바뀝니다(예: `DRAFT → CONSENTED → PROFILED → DOCS_SUBMITTED → UNDER_REVIEW → APPROVED → TERMS_SET → PRICED → EXPLAINED → CONTRACTED → (COLLATERAL_SET) → DISBURSED → COMPLETED`). 순서를 건너뛰면 `InvalidTransition`으로 막히고, 모든 이동은 `application_status_history`와 감사 로그에 남습니다.

## 4. DB 설계

### 4.1 작성 규칙 (팀 공통 `docs/db/db-design.md` 준수)

- 금액 `BIGINT`(원), 금리 `NUMERIC(6,4)`(연 %), enum은 `VARCHAR + CHECK`, JSON은 `JSONB`(SQLite에서는 텍스트)
- ID는 `VARCHAR(40)` 접두어+ULID (예: `lap_01J…`), 계약 번호는 업무 번호 `LA-2026-NNNNNN`(대환 `RA-…`), UNIQUE
- 같은 영역 안은 FK, **다른 서비스(회원·로그인·은행·카드)는 FK 없는 논리 참조 빈 칸**(NULL 허용, `-- @ext` 표시)
- 민감값은 원문 저장 금지: 계좌번호·사번은 마스킹본 + HMAC 해시만, 감사 로그는 내용 해시만
- `schema.sql`의 `-- @domain`, `-- @ext` 태그를 `tools/make_erd.py`가 읽어 ERD를 다시 그림 → 스키마를 고치면 ERD 재생성만 하면 됨

### 4.3 외부 서비스 연결 지점 (지금은 빈 칸)

| 외부 서비스 (예정 테이블) | 대출 쪽 빈 칸 (테이블.컬럼) | 통합할 때 할 일 |
|---|---|---|
| 회원·개인정보 (`members.id`) | loan_application.member_id, loan_account.member_id, inquiry_cache.member_id, notification.member_id, household_info.spouse_member_id | `members(id)`로 FK 추가, 로그인 회원 ID를 신청 시작 시 채움 |
| 로그인·인증 (`auth_session`, `e_sign`) | loan_application.auth_ref, consent_record.auth_ref, contract.signature_ref | 본인인증 세션·전자서명 결과의 참조값을 기록 |
| 은행(계좌) (`accounts`, `account_transactions`) | disbursement.account_id, disbursement.account_txn_ref, loan_terms.auto_debit_account_id, pricing_preference.account_id, loan_account.debit_account_id, payment_txn.account_txn_ref | 지급·자동이체 계좌를 계좌 ID로 연결, 실제 이체 거래 ID 기록 |
| 카드 (`cards`) | pricing_preference.card_id | 카드 실적 우대금리 판정 시 카드 ID 연결 |
| 메인 화면 (홈 대시보드) | (테이블 연결 없음) loan_account · product_catalog · notification 조회 | 로그인 회원의 `member_id`로 "내 대출 요약·상품·알림"을 읽는 조회 API |

> 통합 절차 예: ① 회원 테이블 생성 → ② `ALTER TABLE loan_application ADD FOREIGN KEY (member_id) REFERENCES members(id)` (PostgreSQL) → ③ `Session.start()`에 로그인 회원 ID 전달. 대출 내부 로직은 바꿀 필요가 없습니다.

## 5. 보안·오류 방지 가드레일

| 구분 | 적용 내용 | 위치 |
|---|---|---|
| SQL 주입 방지 | 모든 쿼리 바인딩 강제(params가 튜플/딕셔너리가 아니면 거부), 여러 문장 실행 거부, insert/update는 **실제 스키마에 있는 테이블만** 허용·식별자 검증, WHERE 없는 전체 갱신 금지 | `database.py` |
| 트랜잭션 | SAVEPOINT 기반 중첩 트랜잭션, 예외 시 전부 롤백 | `database.py` |
| 감사 로그 | 모든 상태 변경·실행·상환을 기록, 직전 행 해시를 이어 붙인 **해시 체인**(위변조 탐지), DB 트리거로 **수정·삭제 차단** | `database.py`, `schema.sql` |
| 상태 머신 | 허용된 단계로만 이동, 약정 전 실행 등 건너뛰기 차단 | `state_machine.py` |
| 동의 게이트 | 필요한 동의가 없으면 외부 조회(신용·공공·마이데이터) 자체를 하지 않고 `inquiry_log`에 BLOCKED 기록 | `consent.py` |
| 속도 제한 | 같은 신청·같은 출처 조회를 분당 횟수로 제한 | `security.py` |
| 입력 검증 | 타입·범위·허용 목록·길이·제어문자·태그 문자(`< > { } \``) 차단, 한도 초과 시 "한도금액을 초과하였습니다." | `validation.py`, `cli.py` |
| 개인정보 보호 | 계좌번호·사번 원문 미저장(마스킹 + HMAC), 로그 출력 전 주민번호·전화·계좌 패턴 자동 마스킹, LLM에 보내기 전 마스킹 | `security.py`, `llm_gateway.py` |
| 이중 실행 방지 | 대출 실행·중도상환에 멱등 키(UNIQUE), 같은 키 재요청은 `DuplicateRequest` | `application.py`, `management.py` |
| 대환 사가 | 견적→실행 보류→상환 송금→완제 확인, 어느 단계든 실패하면 보상(지급 취소·사가 COMPENSATED·신청 REFI_FAILED), 대출 계좌 미개설 | `refinance.py` |
| 파일 검사 | 확장자 허용 목록, 10MB 이하, **파일 앞부분 시그니처가 확장자와 일치**하는지(위장 실행 파일 차단), SHA-256 기록 | `evidence.py` |
| LLM 가드레일 | 기본은 외부 호출 없는 offline 제공자, 출력 검증 V1 스키마·V2 대상 실재·V3 수치 일치·V5 금지 표현·V6 필수 문구(+추천 V4·V7·V8·V9), 하나라도 실패하면 고정 문구로 대체, 호출은 `llm_call_log`에 마스킹 기록. 외부 LLM은 키·계약이 없으면 차단 | `llm_gateway.py`, `recommendation.py` |
| 규제 한도 | DSR 40%(스트레스 +1.0%p), LTV·전세 비율, 최종 금리 법정 최고 20% CHECK, 적합성 상환 부담률 70% | `config.py`, `underwriting.py`, `schema.sql` |
| 금액 계산 | `Decimal`로 계산, 상환 스케줄은 원 단위 정수로 잔액 추적 → **원금 합계 = 대출금, 마지막 회차 잔액 0원** 보장 | `calculators.py` |
| 오류 표시 | 업무 오류는 고객용 문구만 표시(`user_message`), 예상 밖 오류는 스택트레이스 대신 일반 안내 + 마스킹된 로그 기록 | `errors.py`, `cli.py` |
| 비밀 관리 | 비밀키는 환경 변수 또는 `data/.secret_key`(git 제외), `data/`(DB·로그) 전체 `.gitignore` | `security.py`, `.gitignore` |

## 6. 점검 결과 (이번 작업에서 찾아 고친 문제)

| # | 발견한 문제 | 조치 |
|---|---|---|
| 1 | 대환 유불리 LLM 문구(RLLM-3)에 허용 수치를 비워 넘겨 항상 검증 실패 → 고정 문구로만 표시 | 순 절감액·대환 비용 숫자를 허용 목록으로 전달 |
| 2 | 추천 사유 문구의 "1위보다"의 숫자 1이 허용 수치에 없어 추천 9건 중 8건이 대체 문구로 빠짐 | 표현을 "첫 번째 추천안보다"로 변경 → LLM 대체 0건 |
| 3 | 원리금균등 상환 스케줄의 원금 합계가 반올림 누적으로 1원 어긋남 | 원 단위 정수로 잔액을 추적하도록 계산 방식 변경 |
| 4 | 이름 등 자유 입력에 `<script>` 같은 태그 문자가 통과 | 태그 문자 차단 추가 |
| 5 | 감사 로그를 DB에서 직접 수정·삭제할 수 있음 | 추가 전용 트리거 추가(우회 수정은 해시 체인 검사에서 탐지) |
| 6 | 존재하지 않는 테이블·WHERE 없는 UPDATE를 막는 장치 없음 | 테이블 허용 목록·빈 조건 차단 |

## 8. 한계와 통합 시 할 일

- **외부 연동은 자리만 있음**: 신용평가·공공기관·마이데이터·보증기관·은행 이체는 체험용 데이터로 대신합니다. 실제 연동 시 `consent.gate()`를 통과한 뒤 호출하도록 같은 위치에 연결하면 됩니다.
- **외부 LLM**: 지금은 offline 제공자만 동작합니다. 자체 게이트웨이 API를 만들면 `llm_gateway.py`의 제공자 클래스만 바꾸면 되고, 검증·대체·기록 흐름은 그대로 유지됩니다.
- **회원·로그인·은행·카드·메인 화면**: 4.3절의 빈 칸에 FK·API만 연결합니다. 통합 전까지는 NULL입니다.
- **동시성**: 체험용 단일 사용자 기준입니다. 서버(여러 사용자)로 옮길 때는 PostgreSQL의 행 잠금과 멱등 키 UNIQUE 위반을 `DuplicateRequest`로 바꾸는 처리를 추가해야 합니다.
- **화면**: 콘솔 메뉴로 로직을 체험하는 단계이며, 웹 화면(프로토타입 HTML)과의 연결은 `Session` 메서드를 API로 감싸면 됩니다.
